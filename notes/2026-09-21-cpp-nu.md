# Le C++ nu : loom sans AdaptiveCpp, le CPU d'abord

Session du 2026-09-21. Ce qui a été décidé, ce qui a été fait, ce qui reste.

## Le point de départ

`2d_des_familles` avait montré que le même algorithme monte à 7.6× sur huit cœurs en C++ nu et à
2.1× sous SYCL, avec 115× moins de défauts de cache par cellule (JOURNAL § comparatif). Une partie
tenait à la forme du code (cellule sur la pile contre tampons FFI globaux), mais c'est le modèle
SYCL qui y poussait, et le reste de la chaîne pesait : 1010 lignes pour bâtir acpp + Boost, un
`generic` JIT qui imposait `RTLD_GLOBAL`, 20 s de compilation par noyau CPU, ~1 min par noyau
GPU. Décision : **C++ nu et CUDA**, chaque cible avec son code, et un aiguillage par méthodes --
jamais un `if ( device )` dans le code commun.

## Les décisions

* **foncteurs nommés**, pas de lambdas dans ce que loom génère : nvcc est à l'aise avec une
  `struct` à portée d'espace de noms dont `operator()` est un membre template explicite, et
  renâcle sur les lambdas qui traversent vers le device. Les types des arguments restent des
  paramètres de template déduits à l'appel (c'est `make_available` côté C++ qui décide ce que le
  noyau reçoit, la zone mémoire noyau).
* **l'aiguillage est le type de la queue** en C++ et **`Device.compiler`** en Python. `run_parallel`
  ne connaît aucun device : il pèle les catégories, rend les arguments disponibles et appelle
  `submit_kernel( queue, ... )` / `submit_kernel_grouped( queue, ... )`, une surcharge par queue
  trouvée par ADL. Ajouter un device = sa queue, ses deux `submit_kernel`, son `Compiler`.
* **deux seuls `#if` sur la cible**, dans les shims : `atomic_add.h` (`std::atomic_ref` /
  `atomicAdd`) et `math.h` (`std::sqrt` / `::sqrt`) -- une intrinsèque n'a pas d'autre forme.
  Le code métier écrit `sdot::sqrt`, jamais `std::` ni `sycl::`.
* **répartition par blocs contigus** sur CPU (celle du banc), pas en foulées : chaque fil
  virtuel `t` traite `[ t n / T, ( t + 1 ) n / T )`. `thread_index` reste unique et stable.
* **CUDA à l'étape 3**, avec le découpage en couches entre les deux : le contrat est posé
  (`CudaQueue.h` est un `#error` nommé, `Nvcc` un `Compiler` qui refuse), rien d'écrit à
  l'aveugle.

## Ce qui a été fait

Côté C++ (`loom/include/loom/support/`) :

    kernels/CpuQueue.h        la file de threads persistante (`CpuThreadPool`, workers endormis sur
                              une condvar, `SDOT_NB_THREADS`, `SDOT_PIN_THREADS`) ; `CpuQueue` la
                              poignée copiable ; `submit_kernel` (plat, réductions par fil) et
                              `submit_kernel_grouped` (groupe = `group_size` fils système autour
                              d'un `std::barrier` -- correct, lent, pour tester sur CPU un noyau
                              écrit pour les groupes GPU ; `group_size == 1` retombe sur le plat)
    kernels/QueueEvent.h      sans SYCL : `waiter` vide = déjà complet ; `Dependencies` = waiters
    kernels/Reducer.h         `plus`, `maximum`, `minimum` avec identité ; `Reducer` (`combine`, `+=`)
    kernels/Group.h           `CpuGroup` / `CpuSubGroup` : `group_barrier`, `get_local_linear_range`
    kernels/run_parallel.cxx  ne fait plus que peler et déléguer
    atomic_add.h, math.h      les shims
    common_macros.h           `HD` / `HD_INLINE` (vides hors nvcc)

Supprimé : `RunTraits.h`, `MemorySpace_GlobalCudaRam.h`, `MemorySpace_PinnedCpuRam.h` (morts),
`test_sycl_add.cpp`. `sdot/Queue.h` n'inclut plus que la queue CPU ; le source généré inclut
l'en-tête de SA queue (`Device.cpp_queue_include`) avant.

Côté Python (`loom/src/loom/`) :

    compilation/Compiler.py   `Compiler` (contrat), `HostCxx` (`-O3 -march=native`, signature =
                              compilateur + flags + modèle de CPU), `Nvcc` (étape 3)
    compilation/__init__.py   `make_library` / `make_executable` communs (cache disque, `.srchash`),
                              `cache_root`, `include_dirs` ; `adaptive_cpp.py` supprimé
    compilation/FfiCode.py    `preamble_for` (le foncteur, à portée d'espace de noms) + `code_for`
    devices/*.py              `compiler`, `cpp_queue_include`, `device_is_present` ; plus d'`acpp_*`
    drivers/JaxFfi.py         clé de cache = source | `compiler.build_signature` ; `{preamble}`
    toolchain.py              `sdot-toolchain` : ce que chaque device compilerait avec

## Les chiffres

Compilation d'un noyau CPU : **~4.5 s** (`test_call`, 23 noyaux en 109 s) à **~7 s** (`test_Cell`)
contre ~20 s sous acpp `omp`. Un fichier de 40 entrées : 4 min 25 contre ~15-30 min.

`pd accelerated`, 1e6 germes 2D, FP32, leaf 10, Xeon W-2145 (16 fils) :

| | mesures |
|---|---|
| acpp `omp` AOT, `-O3 -march=native` (avant) | 0.22 s |
| C++ nu, 16 fils | 0.207 s |
| C++ nu, 16 fils épinglés (`SDOT_PIN_THREADS=1`) | **0.190 s** |
| C++ nu, 8 fils | 0.235 s |
| banc `2d_des_familles`, arbre, 8 cœurs | 0.213 s |

Au niveau du banc sur le chemin arbre. Le chemin grille du banc (0.164 s) reste devant : il n'a
pas été porté.

Tests : `test_call` 16/16, `test_group_kernel` 4/4, `test_Cell` 40/40, `test_PowerDiagram` 68/68,
`test_OtPlan1d`, les tests C++ de `loom/tests/cpp` (Tuple, TupleRep, Vector, Matrix, TensorView
avec les réductions) -- tout sur CPU.

## Le pas 2 : le graphe de compilation (même jour)

Mesuré d'abord, sur `power_diagram_measures` (10.6 s en tout) : en-têtes 2.2 s (dont XLA 1.4),
instanciation 1.1 s, génération de code 3.7 s, optimisation 3.6 s. Un en-tête précompilé rend
1 s pour 176 Mo par signature : pas retenu. Le temps est dans ce que chaque unité INSTANCIE --
d'où le mécanisme des sources de domaine (compilées une fois par configuration, liées), et non un
découpage de la glu. `-fvisibility=hidden` fait passer le `.so` d'un noyau de 5.5 Mo à 0.3 Mo.

Fait :

    compilation/build.py      le graphe : `Build.object( src, defines )`, `shared_library`,
                              `executable`, `runtime_library` ; manifeste JSON sur disque
                              (`build/ninja/manifest.json`), `build/build.ninja` réécrit, verrou
                              de fichier, `ninja` sur les seules cibles demandées
    Compiler.ninja_rules()    les règles (compile avec `-MMD`, link) viennent du compilateur ;
                              `rule_for( src )` choisira nvcc pour un `.cu`
    loom/cpp/runtime/         `libloom_runtime_<sig>.so` : la file de threads du processus
                              (`CpuThreadPool.h` + `cpu_thread_pool.cpp`), UNE par processus ;
                              chaque `.so` généré la lie (rpath)
    FfiCode( sources = ... )  `( "x.cpp", { "DEF": "v" } )` : une unité par (source, defines,
                              compilateur), partagée -- `loom/tests/test_sources.py`
    LOOM_EXPORT               ce qu'une bibliothèque publie ; tout le reste est caché

Retiré : `cpp_sources_hash` / `.srchash` / les niveaux de `SDOT_FORCE_BUILD` (la variable force
maintenant la cible demandée, rien d'autre). Vérifié : toucher un en-tête ne rebâtit que les
unités qui l'incluent (`Group.h` -> les noyaux, pas le runtime ; `SumOfGaussians.cxx` -> rien
pour `test_call`). Le source généré est écrit seulement s'il change (les dates font foi).

## Ce qui reste

1. **Les sources de domaine côté sdot** : le mécanisme existe, aucun noyau ne l'utilise encore.
   Le candidat : `diagram::measures` & co. compilés une fois par (dim, TF, densité, accélérateur)
   derrière une forme canonique des agrégats -- c'est une décision de design sdot (quelle forme
   canonique), à prendre avec l'utilisateur.
2. **CUDA** (étape 3) : `CudaQueue.h` (`__global__` template sur un flux, `CudaGroup` sur
   `__syncthreads`, `__shared__` pour `local_scratch`, `cudaEvent` dans `QueueEvent::waiter`),
   `Nvcc.command`, les lambdas internes (`TensorView::fill_with`) en foncteurs, la synchro avec
   le flux XLA (l'expérience `LOOM_XLA_STREAM_SYNC` est encore dans `JaxFfi._render_call`).
3. **Les wheels** (étape 4) : variantes `-march` (x86-64-v2/v3/v4, arm64), choix à l'import,
   catalogue / atelier. `containers/*.def` et `scripts/validate_wheel.py` bâtissent encore acpp.
4. `otrec/.../sycl_kernel.py` et `dirac_sycl.py` (le noyau SYCL fusionné d'otrec) ne sont pas
   touchés : `_find_acpp` retombe sur `acpp` du PATH.
