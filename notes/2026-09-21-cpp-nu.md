# Le C++ nu : loom sans AdaptiveCpp, le CPU d'abord

Session du 2026-09-21. Ce qui a été décidé, ce qui a été fait, ce qui reste.

## Le point de départ

`2d_des_familles` avait montré que le même algorithme monte à 7.6× sur huit cœurs en C++ nu et à
2.1× sous SYCL, avec 115× moins de défauts de cache par cellule (JOURNAL § comparatif). Une partie
tenait à la forme du code (cellule sur la pile contre tampons FFI globaux), mais c'est le modèle
SYCL qui y poussait, et le reste de la chaîne pesait : 1010 lignes pour bâtir acpp + Boost, un
`generic` JIT qui imposait `RTLD_GLOBAL`, 20 s de compilation par noyau CPU, ~1 min par noyau
GPU. Décision : **C++ nu et CUDA**, chaque cible avec son code, et un aiguillage par méthodes --
jamais un `if ( device )` dans le code commun.

## Les décisions

* **foncteurs nommés**, pas de lambdas dans ce que loom génère : nvcc est à l'aise avec une
  `struct` à portée d'espace de noms dont `operator()` est un membre template explicite, et
  renâcle sur les lambdas qui traversent vers le device. Les types des arguments restent des
  paramètres de template déduits à l'appel (c'est `make_available` côté C++ qui décide ce que le
  noyau reçoit, la zone mémoire noyau).
* **l'aiguillage est le type de la queue** en C++ et **`Device.compiler`** en Python. `run_parallel`
  ne connaît aucun device : il pèle les catégories, rend les arguments disponibles et appelle
  `submit_kernel( queue, ... )` / `submit_kernel_grouped( queue, ... )`, une surcharge par queue
  trouvée par ADL. Ajouter un device = sa queue, ses deux `submit_kernel`, son `Compiler`.
* **deux seuls `#if` sur la cible**, dans les shims : `atomic_add.h` (`std::atomic_ref` /
  `atomicAdd`) et `math.h` (`std::sqrt` / `::sqrt`) -- une intrinsèque n'a pas d'autre forme.
  Le code métier écrit `sdot::sqrt`, jamais `std::` ni `sycl::`.
* **répartition par blocs contigus** sur CPU (celle du banc), pas en foulées : chaque fil
  virtuel `t` traite `[ t n / T, ( t + 1 ) n / T )`. `thread_index` reste unique et stable.
* **CUDA à l'étape 3**, avec le découpage en couches entre les deux : le contrat est posé
  (`CudaQueue.h` est un `#error` nommé, `Nvcc` un `Compiler` qui refuse), rien d'écrit à
  l'aveugle.

## Le pas 2 : le graphe de compilation (même jour)

Mesuré d'abord, sur `power_diagram_measures` (10.6 s en tout) : en-têtes 2.2 s (dont XLA 1.4),
instanciation 1.1 s, génération de code 3.7 s, optimisation 3.6 s. Un en-tête précompilé rend

découpage de la glu. `-fvisibility=hidden` fait passer le `.so` d'un noyau de 5.5 Mo à 0.3 Mo.

## Le pas 3 : CUDA par nvcc (même jour)

L'expérience préalable sur un source généré avait donné deux familles d'erreurs, et rien d'autre :
les lambdas (nvcc ne prend pas un lambda générique comme noyau, même « étendu ») et « calling a
`__host__` function from a `__device__` function » sur chaque fonction atteinte par un noyau.
Sous nvcc, tout ce qu'un noyau touche porte `__host__ __device__` -- c'est LE coût de nvcc, et il
est mécanique : `scripts/annotate_hd.py` (libclang) a posé **705 `HD`** sur `loom/support/
{containers,algorithms,Ct*}` et `sdot/include/sdot` (colonnes préservées ; asimd n'est pas touché,
le noyau à registres n'est instancié que sur CPU). Les fonctions hôte par nature (`make_available`,
`transfer_cost`, `fill_with`, ce qui parle à un `std::ostream`) restent sans. La convention
désormais : toute nouvelle fonction atteignable par un noyau s'écrit avec `HD`.

Ce que nvcc a appris à la chaîne, en plus :

* **`LOOM_TAG( Type, name )`** (`common_macros.h`) pour les objets globaux vides -- les noms d'axes
  de `DEFINE_AXIS`. Un `inline constexpr` de portée globale n'est pas utilisable dans du code
  device dès qu'on appelle `num_vertex = i` avec un `i` non constant (ODR-use) ; la passe device
  de nvcc veut un `__device__`. Troisième `#if` sur la cible, avec les deux shims.
* **un ami template abrégé défini dans une classe template** (`friend void f( const Vector &,
  auto &&func )`) fait perdre à EDG les membres qui suivent (« has no member `_storage` ») :
  `template<class F> friend` épelé, dans `Vector.h`. Antérieur à la refonte (acpp passait par
  clang).
* les `TensorView::fill_with` sont des foncteurs nommés, et `test_call.py` est passé de corps
  `run_parallel( ..., []( auto ... ) {...} )` écrits à la main à `FfiCodeParallel` : ce qu'un
  utilisateur écrit est le corps, loom fait le foncteur.
* **`kernel_form` à la place de `make_available`** : la forme noyau d'un argument (la même vue,
  retypée dans la zone mémoire du kernel) est une VALEUR rendue par `kernel_form( queue, io )`,
  plus une continuation. L'ancienne forme (à la SYCL, `cont( ... )` pour garder vivants des
  tampons de transfert) empilait un lambda par membre de chaque agrégat, et EDG ne déduisait
  plus le type de retour au fond de la chaîne de `measures_bwd` (« cannot deduce the return
  type ») ; aucun de nos devices ne transfère, la chaîne n'avait plus de raison d'être. Le
  générateur d'agrégats émet `kernel_form`, `make_available( queue, io, arg, cont )` reste pour
  les appelants qui passent une continuation. Le source généré ne dépend plus de `sdot/Queue.h`
  (loom ne nomme pas sdot : `namespace sdot { using Queue = SDOT_QUEUE; }` est émis).
* `sdot/Cell._rows` lisait l'item `b` en supposant `nb_items` lignes : sur GPU le batch est
  rembourré à `Device.batch_alignment` (128 octets), l'item `b` est à la ligne `b` d'un tampon
  plus grand.

Le runtime (`loom/include/loom/support/kernels/CudaQueue.h`, `CudaGroup.h`) : `CudaQueue` porte
un flux ; `submit_kernel` lance un `__global__` template (foulées sur les items : coalescence),
les réductions en registres puis `atomic_combine` par CAS dans un scalaire device relu par le
finalizer ; `submit_kernel_grouped` un bloc par groupe, `extern __shared__` pour `local_scratch`,
`CudaGroup` sur `__syncthreads`, `CudaSubGroup` sur le warp (`__syncwarp`). `Ptr::value` / `set`
sur `CudaGlobalMemorySpace` passent par `cudaMemcpy` (`copy`). Le flux est CELUI DE XLA pour
l'appel (`ffi::PlatformStream`, `Device.cpp_stream_param` / `cpp_queue_decl`) : l'ordre avec le
reste du programme est celui du flux, sans synchronisation -- un `QueueEvent` attend quand même
à sa destruction (relectures, réductions).

Le compilateur (`Compiler.Nvcc`) : `nvcc -ccbin <hôte> -arch=<sm de la carte> -std=c++20 -O3
--expt-relaxed-constexpr --extended-lambda`, les flags hôte via `-Xcompiler`, `-MD -MF` pour les
depfiles, `.cu` pour le source généré (`rule_for`), les `.cpp` de domaine par le compilateur hôte,
nvcc lie. **nvcc vient du paquet pip `nvidia-cuda-nvcc-cu13`** (`site-packages/nvidia/cu13/bin/nvcc`,
le même toolkit que le plugin CUDA de Jax, `find_nvcc`) -- un compilateur CUDA sans rien installer
sur la machine, ce qui compte pour l'étape 4.

## Le pas 4, entamé : ce qui est fait, et ce qui est à décider

Fait (même jour) :

* les wheels `loom` et `sdot` sont **cohérentes avec la nouvelle chaîne** : `scripts/validate_wheel.py`
  bâtit les deux (`pip wheel`), les installe dans un venv NEUF avec `ninja` et `jax` de PyPI, et le
  noyau de fumée compile depuis `loom/_include` + `sdot/_include`, le runtime depuis `loom/_cpp`
  -- VALIDATION OK. C'est le mode « atelier » en wheel : il exige un compilateur sur la machine.
* loom ne nomme plus sdot : chaque paquet **enregistre sa racine C++** à l'import
  (`loom.compilation.register_include_root`, fait dans `sdot/__init__.py`), d'un checkout ou d'un
  wheel. `include_roots()` remplace `cpp_include_root` / `additional_include_dirs`.
* `SDOT_CPU_VARIANT=x86-64-v3` (ou `v2`, `v4`, `armv8-a`) compile pour un NIVEAU d'architecture
  au lieu de `-march=native`, avec le niveau pour signature -- un binaire à emporter, et l'unité
  du catalogue. `cpu_variant()` dit le niveau le plus riche que la machine porte (via numpy,
  `X86_V2/V3/V4`).

Mesuré en fin de journée (`job -b`, la machine pour lui seul, 1e6 germes 2D FP32, leaf 10, avec
la mémoire des voisins de `99ec277`) : **CPU natif 0.114 s, CPU `x86-64-v3` 0.120 s, 2080 Ti
0.090 s** (boucle mémoire, sans moteur à registres). Le niveau v3 rend 5 % au natif : une
variante v3 du catalogue vaut presque le natif sur ce Xeon AVX-512.

À décider, pour le catalogue (des noyaux précompilés dans les wheels) :

1. **Quels noyaux.** L'ensemble est une matrice (noyau × dtype × dim × densité × accélérateur ×
   axes de batch) que rien n'énumère aujourd'hui. Deux voies : ENREGISTRER ce que les tests et
   bancs compilent (`SDOT_RECORD_KERNELS=dir` : loom y dépose chaque source généré avec sa clé),
   et bâtir ce relevé par variante -- pragmatique, exhaustif pour ce qui est testé ; ou DÉCLARER
   sur chaque `FfiCodeParallel` son espace de configurations -- plus propre, plus de travail. Je
   pencherais pour l'enregistrement d'abord.
2. **Un `.so` par noyau ou une bibliothèque par variante** (`libsdot_kernels_x86-64-v3.so`, toutes
   les entrées dedans, un seul `dlopen`). 200 noyaux × 3 variantes × 0.3 Mo ~ 180 Mo par wheel en
   `.so` séparés ; la bibliothèque unique partage le runtime et pèse moins. Le graphe sait déjà
   lier N objets en une bibliothèque.
3. **Les plateformes** : manylinux x86-64 (v2/v3/v4), macOS arm64, Windows ? Et pour CUDA : un
   fatbin par majeur de toolkit (`-gencode` sm_70..sm_90 + PTX), et surtout le fait que nvcc
   vient de pip rend l'atelier CUDA possible sans toolkit installé.
4. **La clé de recherche** : aujourd'hui `hash( source | signature du compilateur )` où la
   signature porte le modèle de CPU (`-march=native`) ; pour le catalogue elle porte la variante.
   À l'import : variante détectée -> bibliothèque -> entrée par hash de source ; à défaut,
   atelier si un compilateur est là, sinon une erreur qui nomme ce qui manque
   (`SDOT_KERNELS=catalogue|atelier|auto`).

## Le catalogue (2026-09-22)

Décidé avec l'utilisateur : le relevé par PROVOCATION (un script exerce l'usage standard, on
récupère ce qui a été compilé), UNE bibliothèque par variante, Linux x86-64 v2/v3/v4 + macOS
arm64 + CUDA, et l'objectif « rapide pour l'usage standard » -- le reste se compile sur place.

Ce qui existe (`loom/compilation/catalogue.py`, `scripts/build_catalogue.py`,
`python -m sdot.catalogue`) :

* **Relevé** (`build_catalogue.py record --device cpu|cuda`, sur une machine de dev -- un GPU
  pour la partie CUDA, car il faut EXÉCUTER les appels) : `SDOT_CATALOGUE_RECORD` fait déposer par
  `compile_and_register` chaque source généré dans `catalogue_record/<cpu|cuda>/`, avec ses
  sources de domaine, et les en-têtes générés dans `catalogue_record/include/`. Versionné : c'est
  le relevé que l'intégration continue compile, sans GPU. Un relevé périmé ne se voit pas à la
  compilation mais à la validation (`SDOT_KERNELS=catalogue` refuse de compiler).
* **Compilation** (`build_catalogue.py compile --variant x86-64-v3`, ou `--device cuda --arch
  sm_70,...,sm_90`) : chaque source en objet (`-DSDOT_FFI_ENTRY=sdot_ffi_<clé>` : le point
  d'entrée est un define, pas un mot du source), tout lié -- runtime compris -- en
  `sdot/catalogue/<tag>/libsdot_kernels.so` (7.6 Mo pour 101 noyaux CPU) + `catalogue.json`.
  Le wheel `sdot` embarque `sdot/catalogue/` (-> `sdot/_catalogue`).
* **Recherche** : la clé = hachage( source | sources de domaine (chemins relatifs) | tag ) --
  rien de la machine ni du compilateur. À l'import `sdot` enregistre son `_catalogue` ; à l'appel
  `lookup` essaie les tags que la machine porte, du plus riche au plus pauvre (`Cpu.catalogue_tags`
  : v4, v3, v2 sur ce Xeon). **Rien à parcourir ni à valider** : le wheel embarque en-têtes et
  catalogue bâtis ensemble. Un checkout n'enregistre un catalogue que si `SDOT_CATALOGUE_DIR` le
  nomme (ses en-têtes bougent, un catalogue par défaut servirait des binaires périmés).
* `SDOT_KERNELS=auto|catalogue|atelier` (atelier = compiler sur place, ce qu'un checkout fait).

Vérifié : `python -m sdot.catalogue --device cpu` sous `SDOT_KERNELS=catalogue` avec un build
vide -- tout l'usage standard tourne sans une compilation.

`.github/workflows/wheels.yml` : sur un tag `v*`, manylinux_2_28 (v2/v3/v4 + CUDA par le
compilateur de pip) et macOS 14 arm64, wheels `py3-none-<plateforme>` pour `sdot` (binaires sans
ABI python), validation finale sous `SDOT_KERNELS=catalogue`. Non exécuté ici.

Aussi : `containers/` réduit à `cpu.def` et `cuda-jax.def`, sans acpp, LLVM ni toolkit système
(le compilateur CUDA vient de `jax[cuda13]`) ; `Tuple<>::size` / `Tuple( Values )` en `inline`
(des définitions par unité, insupportables dans une bibliothèque qui en lie cent).

## Ce qui reste

1. **Les sources de domaine côté sdot** : le mécanisme existe, aucun noyau ne l'utilise encore.
   Le candidat : `diagram::measures` & co. compilés une fois par (dim, TF, densité, accélérateur)
   derrière une forme canonique des agrégats -- c'est une décision de design sdot (quelle forme
   canonique), à prendre avec l'utilisateur.
2. **CUDA, la suite** : `detach()` des événements quand rien n'est relu (aujourd'hui chaque
   `run_parallel` attend le flux) ; un binaire multi-architectures ; la performance GPU n'a pas
   été mesurée.
3. **Le catalogue** (étape 4, suite) : voir ci-dessus. `containers/*.def` bâtissent encore acpp.
4. `otrec/.../sycl_kernel.py` et `dirac_sycl.py` (le noyau SYCL fusionné d'otrec) ne sont pas
   touchés : `_find_acpp` retombe sur `acpp` du PATH.
