# 2026-09-24 — `errand` : sortir le runner du dépôt

Le runner `test`/`bench`/`experiment` (`./run`, `loom.cli`, `loom.testing`) a un public bien plus
large que le transport optimal et zéro rapport avec le sujet. Il part dans son propre dépôt, sous le
nom **`errand`** (distribution `errand-run`) : *une course qu'on fait pour quelqu'un, et dont on
revient avec les choses*.

## Ce que c'est, et ce que ce n'est pas

> py.test répond à « est-ce que ça passe ? ». `errand` répond à « exécute ce travail — ici, dans ce
> conteneur, sur cette machine — et RAPATRIE tout ce qu'il a produit dans un chemin que je sais
> prédire ».

L'outil tient sur DEUX jambes, et il ne vaut rien sans les deux :

- **Où et comment ça tourne.** Un environnement est une pile de couches — micromamba, conda, venv,
  conteneur, autre machine, n'importe quelle combinaison. `errand` les déclare, les CONSTRUIT
  d'après ce qu'elles disent avoir besoin, vérifie avant chaque run qu'elles n'ont pas dérivé, les
  sélectionne par tag, et lance le même travail sur une MATRICE d'environnements en une invocation.
- **Ce qui revient.** Chaque exécution a un répertoire de sortie dont le chemin est calculé, pas
  inventé.

C'est ce qui lève le recouvrement avec py.test : **py.test n'a aucune notion de _où_, ni aucune
notion du répertoire de sortie comme faisant partie du résultat.** Les trois choses à mettre en
avant :

1. **Le rapatriement déterministe.** Le contrôleur local PRÉDIT le chemin exact qu'écrira le
   processus distant (mêmes règles de hash/date des deux côtés) et ne rsync que celui-là. Pas de
   marqueurs déclarés à l'exécution, pas de « ramène tout `tmp/` » — `tmp/` n'est pas remis à zéro
   par le push, un hôte distant porte des runs anciens sans rapport.
2. **Le chemin comme index.** `{kind}/{fichier}__{nom}/[hash-params]/{env}/[date]/`. L'historique et
   la comparaison entre machines sortent de l'arborescence, pas d'une base. Les `summary.yaml` sont
   recalculés en relisant le disque : auto-réparants, corrects quel que soit le nombre
   d'invocations qui y ont contribué.
3. **Une machine distante est un layer, pas un concept.** `[Remote(...), Apptainer(...)]`, et
   `--env lmo-cuda` marche sur toutes les commandes sans qu'aucune ne sache ce qu'est ssh.

Non-but : construire sur py.test (le modèle deux phases + identité par site d'appel + rechargement
par entrée y est incompatible, et c'est justement la valeur).

Le parallélisme, en revanche, est un BUT et pas un non-but (revirement du 2026-09-24, second
passage) : les tests tournent en parallèle, un `bench` prend la machine pour lui seul, la file est
partagée entre toutes les invocations sur l'hôte — c'est-à-dire exactement la sémantique du `job`
de la machine. Un chronométrage pris pendant qu'autre chose tournait n'est pas un chronométrage :
ce n'est pas une optimisation, c'est ce qui fait qu'un `bench` veut dire quelque chose. Sur un
cluster, la vraie file est celle de Slurm et `errand` doit y soumettre (`r.scheduler`).

## Décisions prises

| point | décision |
|---|---|
| nom | `errand`, import `errand`, distribution `errand-run` (PyPI `errand` est un squat mort de 2021) |
| langue | doc et commentaires en ANGLAIS, comme le reste du code |
| branchement | le `./run` du projet est un vrai script qui CONSTRUIT un `Runner` — pas de fichier à nom magique, pas de crochet implicite, pas d'entry-points |
| périmètre | un seul paquet, deux modules : `errand.layers` importable sans le harnais, et réciproquement |
| dépendances | stdlib seule pour le cœur (`./run env create` tourne AVANT que l'env existe) ; YAML en extra, JSON en repli |
| providers | une entrée n'est PAS forcément un site d'appel Python (voir plus bas) |
| migration | `loom.testing` devient un shim de ré-export ; les ~30 fichiers d'entrée ne bougent pas tout de suite |
| tags | `Driver("jax", pip=…)` se scinde en `Tag( name, value )` (métadonnée) + `Pip( spec )` (layer d'install) ; un seul langage d'expression pour `--tag`, `--only` et `has_tag` |
| ordre de marche | on écrit `errand` SEUL d'abord — doc, puis code, puis exemples — et on ne branche loom/sdot que quand c'est stable |
| répertoire de sortie | `runs/` par défaut, configurable (`tmp/` est un nom de nsdot) |
| `result.yaml` | gagne `host`, `commit` (+ `dirty`) et la version d'errand : sans ça un historique entre machines n'est pas opposable |
| `build-sif` | disparaît, absorbé par `./run env create` — une couche sait se sonder et se créer, ou pas |

## La forme publique

```python
#!/usr/bin/env python3
from errand import Runner, Micromamba, Apptainer, Remote, Tag

r = Runner( prefix = "SDOT", src = [ "loom/src", "sdot/src", "otrec/src" ] )

r.env( "default",  [ Micromamba( "vfs" ), Tag( "jax" ) ] )
r.env( "lmo-cuda", [ Remote( host = "lmo", remote_dir = "…" ),
                     Apptainer( image = "containers/cuda-jax.sif" ),
                     Tag( "jax", pip = "jax[cuda13]" ), Tag( "cuda" ) ] )

r.option( "--device", choices = [ "cpu", "cuda" ],
          env = lambda v: { "SDOT_DEVICE": v } | ( { "JAX_PLATFORMS": "cpu" } if v == "cpu" else {} ) )
r.option( "--fp", choices = [ "FP32", "FP64" ], env = "SDOT_FTYPE" )

r.command( "install",   install_projects )   # la liste loom/sdot/otrec vit ICI
r.command( "toolchain", lambda c: c.run( [ "python", "-m", "loom.toolchain" ] ) )
r.provider( CppProvider( dir = "loom/tests/cpp" ) )

sys.exit( r.main() )
```

`errand/__init__.py` doit rester importable sans rien tirer — les fichiers d'entrée l'importent, et
la découverte les importe TOUS. `Runner` et les layers passent donc par un `__getattr__` paresseux,
comme `loom/cli/__init__.py` le fait déjà.

## Le protocole de provider

C'est le changement structurant. Aujourd'hui `_run_cpp_tests` court-circuite tout : il compile,
lance, rend des échecs, et n'a ni `out_dir`, ni `result.yaml`, ni rollup, ni rapatriement. Dans
`errand`, le cœur cesse de supposer qu'une entrée est un site d'appel Python :

```python
class Provider( Protocol ):
    def files( self )            -> list[ Path ]:  ...   # pour la levée d'ambiguïté des specs
    def collect( self, specs )   -> list[ Entry ]: ...
    def run( self, entry, ctx )  -> Outcome:       ...

# Entry   : provider, key, label, params, tags
# ctx     : out_dir, params résolus, env vars, le filtre `::nom` non consommé
# Outcome : status, error, results, output_text
```

Le provider Python est alors une implémentation parmi d'autres, et c'est LUI qui porte le truc des
deux phases (`if p := bench(...)`), le rechargement du module par entrée et le `_Tee` de capture —
tout l'état mutable global (`test_phase`, `test_filter`, `current_results`) sort du cœur. Une suite
C++, Rust, Julia ou shell se branche exactement pareil, et gagne au passage `out_dir`,
`result.yaml`, les rollups datés et le rapatriement distant : **un `bench` C++ comparé entre
machines, qui n'existe pas aujourd'hui.**

Trois conséquences à ne pas rater :

- **La levée d'ambiguïté des specs est globale.** « un nom de fichier sans `*` doit désigner un
  fichier unique » se vérifie sur l'union des `files()` de tous les providers, pas provider par
  provider.
- **`collect()` tourne aussi du côté LOCAL**, même pour une exécution distante : c'est ce qui permet
  de prédire les chemins à rapatrier. Un provider ne peut donc pas énumérer ses entrées en
  compilant. Pour le C++ ça fixe la granularité : **une entrée par fichier × device**, et la partie
  `::nom` de la spec est passée telle quelle à l'exécutable (ce que `_cpp_filters` fait déjà).
- **La capture de sortie est locale au provider** : `_Tee` pour du Python en processus, le stdout du
  sous-processus pour le reste. Le cœur ne reçoit que le texte, dans l'`Outcome`.

## Second passage sur le README (relecture annotée `@@@`)

Quatre revirements, tous dans le sens de l'utilisateur :

1. **Les trois `kind` deviennent des PRESETS**, pas des catégories. La frontière est artificielle :
   une expérience peut asserter, un banc peut produire une image, un test peut mériter un
   chronométrage. Un seul type d'entrée, quatre traits réglables un par un — `keep` (les chiffres
   sont gardés et comparés), `bulk` (ramassé par un `./run` nu), `exclusive` (la machine pour lui
   seul), `stable_path` (`latest/` est ce qu'on ouvre). Conséquences en cascade : plus de niveau
   `{kind}` dans le chemin (il n'y a nulle part où classer une entrée qui est plusieurs choses) ;
   plus de sous-commandes `test`/`bench`/`experiment`, juste `./run [motif]` avec un filtre `-k` ;
   le balayage autorisé partout, tests compris.
2. **Le parallélisme est un but** (voir plus haut).
3. **Les tags sont des DIMENSIONS NOMMÉES**, déclarées une fois, chacune donnant son propre drapeau
   (`--fp 64` plutôt que `--tag fp=64`), et portant les variables d'environnement qu'elle implique
   (`env = lambda v: …`). **`r.option` disparaît** : un tag resserre où ça tourne ET configure une
   fois sur place, un seul mécanisme. Un env qui ne mentionne pas une dimension matche n'importe
   quelle valeur. Le `|` revient dans la grammaire, parce qu'une expression peut légitimement
   désigner PLUSIEURS envs — c'est la matrice, et la virgule y veut dire la même chose que sur un
   paramètre.
4. **La construction et la fraîcheur des environnements passent au premier plan** : un env dit ce
   qu'il lui faut (`requirements.txt`, recette `.def`/`Dockerfile`, specs pip, version de python) et
   `errand` le rend vrai. Empreinte comparée avant chaque run, remise à niveau automatique.
   `install` et `build-sif` fusionnent dans `env setup`, qui ne se tape presque jamais.

Autres corrections : ne pas définir par la négative (« l'unité n'est pas une assertion », « pas un
concept ») ; « dégénéré » → « le plus simple » ; les chemins présentés comme un DÉFAUT configurable ;
`{host}` avant `{env}` (un nom d'env ne veut rien dire hors du projet, `default` ment d'une machine
à l'autre) ; `latest/` en lien symbolique, ce qui permet de tout dater sans coûter le chemin stable
d'une expérience ; un troisième niveau de résumé, par jeu de paramètres, à la racine de l'entrée ;
une direction déclarée par résultat (`Min`/`Max`) pour distinguer un gain d'une régression ; les
providers C++/Rust/JS fournis dès le départ, pas comme extension ; plus de références à `lmo` dans
les exemples ; `env list` plutôt que `env`.

## Troisième passage — le modèle de configuration change

Revirement principal : **`./run` qui construit un `Runner` est abandonné.** `errand` est une
COMMANDE, utilisable sans aucune configuration. Quand il y en a une, c'est un `.errand.py` à la
racine (trouvé en remontant depuis `cwd`), du Python ordinaire importé une fois, avec des fonctions
de registre au niveau module (`configure`, `env`, `provider`) — pas d'objet à construire, pas de
`sys.exit( r.main() )` à écrire. On garde ce qui avait fait rejeter le fichier de conf déclaratif au
premier passage (les crochets sont de vrais appelables), sans le passe-plat.

Conséquences : plus de sous-commandes du tout (`errand --envs`, `--setup`, `--no-setup`) ; et
**`r.command` disparaît** — ce qu'un projet veut lancer est une entrée comme une autre,
`entry( "docs", bulk = False )` la range hors du chemin jusqu'à ce qu'on la nomme.

Le reste du passage :

- **`entry(…)` est la primitive**, documentée en premier ; `test`/`bench`/`experiment` sont trois
  fonctions ordinaires par-dessus, écrites en trois lignes — donc « en écrire une quatrième » n'est
  pas une API (`r.preset` meurt), c'est un appel de fonction.
- **`Min`/`Max` déclarés meurent** : on synthétise systématiquement min ET max des valeurs
  numériques, comme aujourd'hui. Déclarer une direction était pénible pour ce que ça rapporte.
- **Les paquets pip descendent DANS le layer** qui les installe (`Micromamba(requirements=…)`,
  `Apptainer(pip=…)`) : c'est cette chose-là qu'il faut reconstruire quand ils changent.
- **Les tags sont des arguments nommés de `env`** — `env( "gpu", [...], driver = "jax", cuda = True,
  fp = "32|64" )`. Aucune déclaration préalable (`r.tag` meurt) ; les drapeaux `--driver`, `--fp`
  se déduisent des noms vus. Les variables d'environnement d'un env sont un layer `Vars`, pas un
  effet de bord des tags : **un tag SÉLECTIONNE, un layer AGIT.**
- **`--env-tags` / `--entry-tags`**, symétriques et sans ambiguïté de domaine.
- **`{host}/{env}` dans le chemin devient `{place}`** : le nom du conteneur s'il y en a un, sinon
  celui de l'hôte.
- **Le partage des ressources passe en tête** : troisième jambe annoncée dès l'introduction, une
  file d'un fichier par hôte, partagée entre invocations. `-j` est relégué (ça ne concerne presque
  personne).
- **Slurm devient un layer de premier plan** (`Slurm( partition =, gpus =, time = )`), à côté de
  `Ssh` (ex-`Remote`).
- **Les providers quittent le README** pour le wiki : on fournit C++/Rust/JS par défaut et on espère
  couvrir 99 % des cas ; ce qui reste dans le README est le paragraphe « one line in `.errand.py` ».
- Ne plus justifier par l'historique du projet : le lecteur ne connaît pas le système d'avant et
  s'en moque. Les passages qui argumentaient « contre ce qu'on faisait » sautent.

## Quatrième passage — `--batch` et le suivi

**`--batch` est un MODE, pas un layer.** Il veut dire la même chose partout — lance et rends-moi la
main — et seule la façon de se détacher change : session propre en local, lancé-et-lâché par `Ssh`,
`sbatch` au lieu de `srun` pour Slurm/OAR/PBS. Un layer qui sait se détacher le déclare et répond
ensuite à trois questions sur une poignée (vivant ? dans quel état ? comment l'annuler ?) — c'est la
même forme que la paire sonder/créer qu'il implémente déjà pour se construire.

Le point qui rend tout ça bon marché : **les chemins étant calculés AVANT l'exécution, l'arrivée
d'un `result.yaml` là où on l'attendait est le signal de fin.** Pas de protocole entre les deux
côtés, pas de démon, pas d'accord qui puisse se désynchroniser — l'arborescence de sortie EST
l'état. Et la file qui partage la machine est la même file, donc un banc exclusif détaché prend
quand même l'hôte pour lui seul.

**Le suivi** : `errand --status` (une fois, texte, greppable) et `errand --watch` (vivant,
interactif). Groupé par invocation, parce que c'est l'unité qu'on a soumise et celle qu'on va
comparer ; et à l'intérieur, **la matrice se lit comme un TABLEAU** — paramètres en lignes,
environnements et tags en colonnes — parce que c'est sa forme réelle et qu'une liste plate de huit
lignes cache justement l'axe qu'on faisait varier. Deux axes tiennent à l'écran, au-delà les
suivants passent dans le libellé de ligne. Les cellules montrent le temps écoulé pendant, le chiffre
gardé après. Le moniteur ne porte aucun état : il sonde l'arborescence et les systèmes de batch,
donc on peut le tuer et le relancer, et plusieurs peuvent regarder en même temps.

**Contextes d'exécution ajoutés au tableau des layers** : `Uv`, `Nix`, `Guix`, `Module` (Lmod — la
façon dont un cluster choisit sa toolchain, et rien d'autre ne le couvre), `Podman`, `Oar`, `Pbs`,
`Sge`, `Lsf`. Écartés pour la v1 : provisionner une VM cloud (bien le faire coûte très cher) et
`Adb` (couvert par `Ssh` + compilation croisée).

## Cinquième passage — les questions ouvertes sont tranchées

- **Reconnaître une suite existante : on ASSUME la devinette, mais on l'écrit.** Un provider trouve
  ses entrées comme son écosystème le fait (`pytest`, les `test_*.cpp` d'un répertoire, les cibles
  `cargo`) ; la ligne `provider( … )` dans `.errand.py` EST la déclaration de ce qui sera cherché et
  où, avec des arguments pour dire autre chose. Sans `.errand.py`, `errand` devine tout seul et
  **dit ce qu'il a deviné** avant de lancer quoi que ce soit : pratique pour un premier coup d'œil,
  jamais silencieux, et le remède est d'écrire la ligne. Mise en cache de la découverte (contre les
  mtimes) : plus tard, c'est une optimisation, pas une question de conception.
- **`{place}` = nom de l'hôte, préfixé par celui du conteneur s'il y en a un** — `gpu-box`,
  `cuda.sif@gpu-box`. Les deux comptent et aucun ne suffit : la même image sur deux machines fait
  deux jeux de chiffres, la même machine avec deux images aussi.
- **La file : un créneau tenu enregistre qui le tient et est TOUCHÉ tant que le travail vit.** Un
  créneau dont l'horodatage a rassis est repris, et son détenteur, s'il revient, apprend qu'il l'a
  perdu. C'est la seule façon honnête de distinguer un run tué d'un run long — un banc qui tourne
  depuis six heures ne se distingue d'un cadavre que par le fait que quelque chose respire encore.
  **Le même battement répond pour les poignées détachées** : une poignée n'est jamais crue seule
  (un id Slurm survit à un redémarrage, un pid nu non et se fait réutiliser). Un mécanisme, pas deux.
- **Le registre d'une invocation est LOCAL** : le côté qui a éclaté la matrice est le seul à avoir
  jamais su que ces runs allaient ensemble. Les créneaux, eux, restent par hôte.
- **`-t` (où) et `-e` (quoi)**, formes courtes de `--env-tags` et `--entry-tags`. La mnémonique est
  enseignée dans la doc plutôt que devinée, parce qu'elle ne va pas de soi.
- **TUI d'abord, page web éventuellement plus tard** : les deux montrent le même tableau et
  répondent à la même question, donc il n'y a rien à arbitrer — le terminal passe devant parce que
  c'est là que le travail se fait déjà.
- `runs/` reste le nom par défaut.

La section « Open questions » du README devient une section « Status » à deux entrées : la matrice
hétérogène en une invocation (local + Slurm à la fois, le cas que toute la conception vise et celui
qui a le plus de façons de mal tourner), et ce qu'un résumé doit dire d'une machine à l'autre
(décider qu'une machine a ralenti demande de savoir quelque chose du bruit).

## Sixième passage — les exemples, et ce qu'ils ont cassé

`errand/examples/` : `01-minimal` (aucune configuration), `02-environments` (quatre envs sur trois
machines, matrices, `--batch`), `03-existing-suite` (pytest + Catch2 + cargo adoptés en trois
lignes, sans toucher une ligne des suites). Le fichier de conf s'appelle `errand.py`, pas caché ;
il est chargé PAR CHEMIN, jamais comme un module nommé `errand`, donc il n'occulte pas le paquet
dont il importe (le seul cas résiduel est `python -m errand` depuis la racine).

La matrice hétérogène (portable + cluster en une invocation) n'est plus une question ouverte :
c'est la responsabilité de l'utilisateur. `errand` lance ce qu'on demande où on le demande et
enregistre d'où vient chaque chiffre ; décider de ce qui se compare à quoi ne lui appartient pas.

**Le défaut trouvé en écrivant l'exemple 02** — et c'est exactement pour ça qu'on les a écrits avant
le code. Avec « un tag sélectionne, un layer agit », une dimension que l'env *paramètre* au lieu de
la *porter* explose en un env par valeur : `local`/`local32`/`gpu`/`gpu32`, avec la précision écrite
DEUX fois dans chacun — une fois pour être matchée par `--fp`, une fois pour être passée au fils.
C'est la tension tag/option qui revient par la fenêtre.

Le remède, qui n'ajoute rien au vocabulaire : **`fp = "32|64"` sur l'env (déjà dans la doc, jamais
exercé) plus un `Vars` en forme d'appelable qui relit la sélection** —
`Vars( lambda t: { "DEMO_FTYPE": f"FP{ t['fp'] }" } )`. Un env couvre alors les deux, `--fp 32,64`
fait deux runs DANS un env au lieu d'en choisir deux, et quatre envs redeviennent deux. Un env qui
ne mentionne pas une dimension matche n'importe quelle valeur ; un qui la borne (`fp = "64"` sur
`cluster`) ne matche que celle-là.

## Septième passage — le cœur est écrit

`slots` supprimé au profit de ressources nommées (`cpus`, `ram`, `gpus`) ; `exclusive` reste la
version brutale. Les marques pytest deviennent des tags d'entrée (documenté). `fp = "32|64"` retiré
des exemples : **ne rien dire signifie toutes les valeurs**, et borner (`fp = "64"` sur `cluster`)
signifie celle-là seulement.

Écrit et qui tourne — `errand/errand/` : `entries.py` (les deux phases, `entry` + les trois presets,
traits, `Param`, `has_tag`/`tag`), `expr.py` (la grammaire `& | ! =`), `discovery.py` (candidats par
marqueur texte, specs `fichier[::nom]`, import sous `_errand_scan`), `results.py` (arborescence,
`result.yaml`, résumés), `yamlish.py`, `cli.py`. Pas encore de layers ni d'environnements.
`errand/tests/` : 37 entrées, écrites AVEC errand, toutes passantes.

Trois choses décidées en écrivant le code :

- **La racine n'est plus devinée par git** : `errand.py` en remontant, sinon le répertoire courant.
  Remonter jusqu'à la racine git élargit silencieusement la recherche à tout un gros dépôt quand on
  lance depuis un sous-répertoire — exactement ce qui est arrivé en lançant l'exemple 01.
- **Tout est daté, sans exception**, et `latest` est un lien symbolique. J'avais commencé par
  rendre les expériences non datées ; le lien coûte moins cher et ne perd pas l'historique.
- **Les résumés agrègent PAR CLÉ.** Plier `seconds` et `primes` dans un seul min/max met un
  chronomètre et un compteur dans le même intervalle et ne dit rien d'aucun des deux. Un intervalle
  `[lo, hi]` quand ça a bougé, la valeur nue quand non — une ligne qui n'a pas bougé ne doit pas
  avoir l'air d'avoir bougé.

Un défaut trouvé par les tests : `result.yaml` plantait quand le fichier d'entrée n'était pas sous
la racine (`relative_to`). Dégradé en chemin absolu — un fichier atteint par un lien symbolique ne
doit pas coûter son résultat à une exécution par ailleurs bonne.

## Huitième passage — environnements, et le statut SKIP

`errand/` est un dépôt git à part (ajouté au `.gitignore` de nsdot). Deux commits.

**`errand.py` à la racine OCCULTE le paquet** — `python -m errand` exécutait le fichier de config,
qui s'importait lui-même. Le nom devient **`errandfile.py`** (dans l'esprit de Makefile /
Dockerfile / Justfile) ; `errand.py` reste accepté mais avec un avertissement qui dit exactement ce
qui casse. Le piège que j'avais signalé au moment de choisir le nom était réel.

**SKIP est un statut à part entière**, ajouté pour la remarque sur l'infrastructure absente : un
test qui ne peut pas tourner faute de machine ne doit être ni vert à tort ni rouge à tort.
`need( "ssh_host", "…", example = "gpu-box" )` va chercher dans un `errand.local.py` NON SUIVI ce
que seule cette machine peut fournir, et saute l'entrée en disant quoi écrire et où. Le bilan de fin
liste les sauts avec leur raison et leur remède. `skip( "raison" )` pour le reste.

Écrit : `layers.py` (`Vars`, `Venv`, `Micromamba`, `Conda`, `Uv`, `Apptainer`, `Docker`, `Podman`,
`Ssh` + rsync), `config.py` (le fichier de projet, la sélection par nom / expression / drapeau de
tag, les matrices d'environnements), `setup.py` (empreinte de ce qu'un env déclare, comparée avant
chaque run, remise à niveau automatique), `local.py`. 66 entrées passantes, 3 sautées.

Trois défauts trouvés en écrivant :

- Les `Vars` d'un environnement qui n'enveloppe rien n'étaient jamais appliquées : il sélectionnait
  bien et ne faisait rien. Quand on ne part pas dans un fils, aucune couche ne réécrit de commande,
  donc il faut poser soi-même ce qu'elles voulaient mettre dans l'environnement.
- `yamlish` relisait mal une clé contenant `:` (`0:venv:python3`). Les tests ne couvraient les
  deux-points qu'en VALEUR. Corrigé en citant toute chaîne contenant `:` ou `,`, et en coupant la
  clé hors des guillemets.
- `--env only64 --fp 32` passait en silence en écrasant le tag déclaré. Nommer un environnement ET
  demander un tag qu'il ne peut pas avoir est une contradiction, pas une demande d'écrasement —
  tourner en simple précision sur un env `fp=64` serait un mensonge.

## Neuvième passage — le saut ssh, exercé

**`ssh localhost` suffit, et devient le défaut.** C'est une vraie machine pour tout ce qui compte
ici : vrai ssh, vrai rsync, vrai shell distant, vrai aller-retour par un répertoire qui n'est pas
celui du projet. Seul le matériel est partagé, et ce n'est pas le matériel qu'on teste. Ordre :
ce que `errand.local.py` nomme, sinon localhost s'il répond, sinon SKIP. Le test emporte une copie
d'errand dans le projet (`_lib`, exclu de la découverte), donc il ne demande rien d'installé en
face — c'est la différence entre un test qui tourne chez n'importe qui et un test qui attend qu'on
lui prépare une machine. `local.load` remonte maintenant les répertoires parents, parce qu'il y a
un `errand.local.py` par MACHINE, pas un par répertoire.

Chez nous `ssh localhost` échouait sur la vérification de clé ; d'où `Ssh( options = [...] )`,
passées à ssh ET à rsync — un rsync qui atteint une autre machine que ssh serait un bug très
silencieux. Et `configure( exclude = [...] )` pour les répertoires que la découverte ne doit pas
parcourir.

Quatre défauts trouvés en exerçant :

- **`--n 3,4` (forme espacée) était pris pour le MOTIF.** Au premier passage les drapeaux de
  paramètres n'existent pas encore (il faut le motif pour trouver les entrées, et les entrées pour
  connaître les paramètres), et argparse rendait la valeur de l'option inconnue comme positionnel.
  `--n=3,4` survivait, ce qui l'avait caché tout ce temps. Le motif se lit maintenant à la main
  avant la première passe : ce qui suit une option inconnue lui appartient.
- **Une assertion multi-lignes dans `error` cassait le `result.yaml`** — un échec pouvait corrompre
  le compte rendu de lui-même. Guillemets doubles avec échappements.
- Côté fils, replier toute la pile atteignait la couche `Ssh`, dont la réponse à être repliée est de
  refuser. Seules les `Vars` peuvent agir sans nouveau processus.
- `yamlish.read` levait sur un fichier qui n'était pas le nôtre, au lieu de coûter sa seule ligne au
  résumé.

À faire ensuite : les conteneurs testables sur Mac aussi (Apptainer n'existe pas sur macOS, donc
`Docker`/`Podman` est le défaut portable — même sonde, même empreinte, seul le layer change).

## Dixième passage — les conteneurs

La forme de la commande est vérifiée partout, sans moteur. L'aller-retour par un VRAI conteneur
l'est avec ce qui répond sur la machine — apptainer, docker ou podman — et saute en distinguant
**absent** de **installé mais ne répond pas**, qui ne sont pas le même problème. Rien ne demande de
GPU ni de registre privé : `python:3-slim` et de l'arithmétique. Ici apptainer répond, docker est
installé sans démon, podman est absent : le chemin conteneur est donc exercé pour de vrai (image
construite depuis sa recette, errand qui tourne dedans, résultats qui reviennent, `{place}` =
`image.sif@hôte`, fichiers appartenant à l'appelant, pas de reconstruction quand l'image est
fraîche, reconstruction quand la recette change).

Écrites parce que le README les promettait sans qu'elles existent : `Slurm` (srun ; sbatch sous
`--batch` plus tard), `Nix`, `Guix`, `Module` (`module` est une fonction de shell, pas un
programme, d'où le `sh -lc`), `Podman`.

Trois défauts trouvés en exerçant :

- **`--n=2,3` était lu comme `--no-setup=2,3`.** argparse abrège les options longues, et un
  paramètre est nommé par qui écrit l'entrée — n'importe lequel peut donc un jour être le préfixe
  d'une option à nous. `allow_abbrev = False` : correspondance exacte ou rien.
- **Une image PÉRIMÉE ne pouvait pas être refaite** : apptainer refuse d'écraser sans `--force`.
  Donc le seul cas où reconstruire est tout l'intérêt était le seul qui échouait. `--force`
  toujours, puisqu'on n'appelle `build` qu'après avoir décidé.
- **Un conteneur à démon écrit en root** : l'arborescence de sortie d'un run en conteneur sortait
  appartenant à quelqu'un d'autre, et le run suivant, dehors, ne pouvait même pas l'effacer.
  `Docker` tourne désormais sous l'uid de l'appelant ; `Podman`, sans racine, n'en a pas besoin et
  un `--user` par-dessus mapperait quelqu'un d'autre.

L'exemple 02 gagne un environnement Docker à côté de l'Apptainer — mêmes tags, même empreinte,
mêmes chemins de sortie, seule la couche change, parce qu'apptainer n'existe pas sur un mac.
87 entrées passantes, 1 sautée (Slurm).

## Onzième passage — la file de ressources, et l'interface avec Slurm

`exclusive` voulait dire quelque chose entre les entrées d'un même processus et **rien du tout entre
deux terminaux** — ce qui est précisément le cas qui mord. La file vit donc dehors : un répertoire
de réclamations, **par utilisateur ET par machine** (un home partagé en NFS ferait sinon attendre un
hôte sur le banc d'un autre), un verrou tenu seulement *pendant qu'on décide*, jamais pendant qu'on
travaille. Une réclamation est TOUCHÉE tant que le travail vit ; celle dont l'horodatage a rassis
est reprise. **L'attente est hors de la mesure** : combien de temps la machine a été occupée ne fait
pas partie de combien de temps le travail a pris.

**La réponse à ta remarque sur Slurm** : dans une allocation, errand ne met pas de file du tout. Le
test est la variable d'environnement que tout système de batch pose (`SLURM_JOB_ID`, `PBS_JOBID`,
`OAR_JOB_ID`, `LSB_JOBID`…) ; une seconde file par-dessus n'attendrait qu'elle-même. Ce que le
travail demande est **transmis** à la place : `Context` porte maintenant `needs`, et la couche
`Slurm` traduit les `cpus`/`ram`/`gpus`/`exclusive` des entrées en
`--cpus-per-task`/`--mem`/`--gpus`/`--exclusive`. Une commande dépêchée porte plusieurs entrées,
donc l'allocation est la plus grande d'entre elles et exclusive si l'une l'est. Ce que
l'environnement dit explicitement l'emporte : qui a écrit `Slurm( cpus = 16 )` savait de cette
partition ce qu'une entrée ne peut pas savoir.

Règle générale qui en sort : **les besoins d'une entrée sont honorés par qui possède la machine.**
En local c'est la file d'errand, sous un ordonnanceur c'est lui, et errand lui passe les chiffres.

Un défaut trouvé en testant : `XDG_RUNTIME_DIR` peut être DÉFINI et inexistant (service, conteneur,
cron) — la file essayait alors de créer `/run/user`.

`errand --queue` montre ce que la machine a et ce qui la tient ; `--no-queue` s'en passe. **Le
parallélisme À L'INTÉRIEUR d'une invocation n'est pas fait**, et le README ne le promet plus :
isoler les entrées les unes des autres demande un processus par entrée. 100 entrées passantes.

## Douzième passage — la partition par défaut, et le `/tmp` qui n'est pas partagé

Oui : **omettre `partition` laisse le cluster prendre la sienne**, et ça marchait déjà — `flags()`
n'ajoute que ce qui est dit. Rendu explicite : tout est optionnel dans `Slurm()`, et la valeur par
défaut du cluster est la bonne réponse bien plus souvent qu'un nom recopié du script de quelqu'un
d'autre, parce qu'elle reste juste après un réaménagement. `describe()` dit « default partition ».

Exercé pour de vrai contre `cinaps` (qui a Slurm, partition `LMO-CPU` par défaut) : job 21137 sur
node15, résultats rapatriés. Le test vérifie `SLURM_JOB_ID` dans ce qui revient — sans ça le travail
aurait pu tourner sur la frontale et personne n'aurait vu la différence.

**Le défaut que ça a révélé vaut bien plus que le reste : un nœud de calcul ne partage pas `/tmp`
avec la machine d'où l'on soumet.** Le job atterrit sur une machine qui n'a jamais entendu parler du
répertoire poussé, et le dit sous la forme d'un `chdir` raté suivi d'une erreur d'import — rien qui
désigne la cause. `errand` vérifie maintenant avant de soumettre (`layers.warnings_for`) et le dit
en clair : la racine d'un environnement qui contient une couche de batch doit être sur un système de
fichiers partagé (home, /scratch, /work), pas `/tmp`, `/var/tmp`, `/dev/shm` ni un scratch local.

## Treizième passage — les ressources ATTRIBUÉES

La file comptait ; elle attribue maintenant. Une entrée qui demande `gpus = 1` s'entend dire
**laquelle**, par `CUDA_VISIBLE_DEVICES` (et les orthographes HIP / ROCR). Compter seul les laissait
toutes prendre la première : deux bancs sur la même carte, et aucun des deux ne mesure quoi que ce
soit. Un run exclusif les reçoit toutes. `_fits` rend désormais `( ce_qu_on_attend, cartes )`, et
`claim` donne un `Granted( path, devices )` dont `env()` est ce qu'il faut poser sur le fils.

Les réclamations s'emboîtent correctement : `CUDA_VISIBLE_DEVICES` renumérote depuis zéro pour celui
sur qui on le pose, donc un processus à qui on a donné les cartes 2 et 5 les voit comme 0 et 1 — et
doit transmettre 0 et 1, pas 2 et 5. `queue.devices()` lit l'existant avant de compter.

Le verrou s'appelle `lock-<machine>` (ta remarque). Le répertoire portait déjà le nom de la machine,
donc c'est une bretelle en plus de la ceinture — mais elle coûte peu et un fichier égaré se lit
alors tout seul.

**Ce qui reste de la gestion des ressources** : le parallélisme à l'intérieur d'une invocation. Ce
n'est pas un réglage, c'est un processus par entrée (l'isolation vient du rechargement, qui n'existe
qu'en un seul processus) : un drapeau `--at fichier:ligne` interne, le parent qui dépêche N fils et
garde leur sortie en bloc plutôt qu'entrelacée, `-j` pour le plafond. La file arbitre déjà entre
eux, donc la mécanique de ressources est faite ; ce qui manque est l'exécution.

## Quatorzième passage — `-j`, un processus par entrée

L'isolation entre entrées EST le rechargement du module, et un rechargement n'isole qu'à l'intérieur
d'un interprète : plusieurs à la fois veut donc dire plusieurs interprètes. Le série reste dans ce
processus-ci (plus rapide, sortie vivante) ; `-j` demande l'autre forme.

- Un fils est désigné par **site d'appel** (`--at fichier:ligne`, interne) et n'a donc qu'UN fichier
  à importer, pas tout l'arbre — sans quoi un processus par entrée coûterait trop cher pour valoir
  la peine.
- Ses paramètres passent par **l'environnement**, pas par des drapeaux : une valeur résolue a le
  droit de contenir une virgule, et une virgule sur la ligne de commande veut dire une matrice.
- Sa sortie est gardée et rendue **d'un bloc**, dans l'ordre d'achèvement. Des lignes entrelacées
  venant de plusieurs entrées sont illisibles et, pire, inattribuables — aucune ne dit de qui elle
  est.
- Ce qu'il est advenu est **relu dans son fichier de résultat**, pas extrait de son bavardage : le
  chemin était connu avant qu'il démarre. Le rapatriement déterministe paie une troisième fois.

**L'interblocage trouvé en testant, et c'est le vrai apport du passage** : une entrée tient une
réclamation pendant qu'elle attend un errand fils, et ce fils attendait une réclamation que son
propre parent ne relâchera pas avant qu'il ait fini. La réclamation se **transmet** donc
(`ERRAND_CLAIM`) — même règle que pour les systèmes de batch : *ce qui a déjà été accordé ne se
redemande pas*. Conséquence pour les tests qui exercent la file elle-même : ils doivent se faire
passer pour un run de premier niveau (effacer `ERRAND_CLAIM` et prendre une file privée), sinon
toute réclamation en dessous devient un no-op.

Mesure sur la suite d'errand (16 cœurs) : **43 s en série, 29 s en `-j 8`**. Modeste, parce que la
suite est dominée par des allers-retours ssh/slurm déjà en attente d'entrées-sorties et par les
entrées exclusives que la file sérialise — ce qui est exactement ce qu'on lui demande.

## Quinzième passage — `--batch` et `--watch`

`--batch` est un MODE, pas une couche : en local une session à soi qui survit au terminal ; par
`Ssh` lancé là-bas et relâché, sortie dans un fichier ; sous Slurm `sbatch` — **qui EST le
détachement**, puisqu'il rend la main dès que le job est en file, donc il n'y a rien à lâcher de
plus. `Context` porte un `batch`, et c'est tout ce qu'il a fallu ajouter aux couches.

Le pari du rapatriement déterministe paie une quatrième fois : **l'arrivée d'un fichier de résultat
là où on l'attendait est le signal de fin.** Pas de protocole entre les deux côtés, pas de démon,
rien qui puisse se désynchroniser. Ce qu'on garde en local est seulement ce que l'arbre ne peut pas
dire : quels runs vont ensemble, et quelle poignée chaque endroit a donnée.

**Le défaut trouvé en exerçant contre cinaps, et c'est une erreur de modèle, pas un bug de plus :
le LIEU d'un run ne se prédit pas.** Un run distant porte le nom de l'autre machine, un job de batch
celui du nœud que l'ordonnanceur a choisi — et personne ici ne le sait. Le répertoire de paramètres,
lui, se prédit (c'est un hachage de ce qu'on a demandé) : on y CHERCHE donc le résultat qui nomme
l'environnement et les paramètres de ce run. Le `result.yaml` porte déjà ces deux champs, donc
l'appariement est exact et rien de nouveau n'a eu à être écrit.

`--status` d'un coup, `--watch` en continu (il ne porte aucun état : il sonde l'arbre et les
systèmes de batch, donc on peut le tuer et le relancer), `--forget` pour retirer une soumission sans
perdre ses résultats. Groupé par soumission, et à l'intérieur la matrice se lit comme un tableau —
paramètres en lignes, lieux en colonnes.

Exercé pour de vrai dans les trois contextes : local, ssh vers cinaps, et sbatch vers sa file
(job 21205 → node15). 125 entrées, rien qui saute.

## Seizième passage — les providers

`Pytest`, `Catch2`, `Cargo`, et le protocole (`files`/`collect`/`run`) dans `providers.py`. La
granularité suit la contrainte, pas le confort :

- **`Pytest` demande à pytest quels sont ses tests** (un plugin `--collect-only` de quinze lignes),
  plutôt que de réimplémenter ses règles — c'est la façon dont un lanceur se met à contredire en
  silence l'outil qu'il enveloppe. Une entrée par test, les marques deviennent des tags d'entrée, et
  le verdict vient du `--junitxml` qui reste dans le répertoire de sortie.
- **`Catch2` est par FICHIER**, parce que les cas d'une suite compilée ne s'énumèrent pas sans la
  construire et que `collect()` doit tourner avant toute construction (c'est ce qui rend les chemins
  à rapatrier prévisibles). Le `::nom` part au binaire comme son propre filtre.
- **`Cargo` interroge `cargo metadata`**, qui connaît les cibles sans en compiler aucune.

Quatre défauts :

- **`errand.provider` (module) masquait `provider` (la fonction de config)** : `provider( Cargo() )`
  dans un errandfile levait « module object is not callable ». Le protocole rejoint `providers.py`.
- **L'errandfile était lui-même découvert comme fichier d'entrée et ré-exécuté**, donc tout ce qu'il
  déclare comptait DOUBLE — providers, environnements, entrées. Indépendant des providers, et il
  attendait là depuis le début.
- `root.find(…) or root.find(…)` : **un `Element` sans enfant est FAUX**, donc les totaux d'un run
  qui passe — une balise auto-fermante — étaient jetés et relus comme zéro assertion.
- Manque de modèle : pour un provider dont les entrées sont des fichiers entiers, le `::nom` ne doit
  pas filtrer l'entrée, il lui est TRANSMIS. D'où `Provider.whole_files`.

Catch2 et cargo sont exercés pour de vrai (compilés, lancés, résultats relus) ; pytest saute faute
d'être installé, ce qui est le mécanisme qui marche — validé à la main dans un venv jetable.
134 entrées, 1 sautée.

## Dix-septième passage — la compilation, et l'installation de ce qui manque

**errand ne compile rien lui-même.** Il lance la commande avec laquelle on construit déjà, **une
fois avant toutes les entrées du provider** — pas une par fichier, et pas une par processus
parallèle, ce qui sous `-j` ferait écrire le même binaire par plusieurs à la fois. D'où un crochet
`prepare( entries, ctx )` appelé une seule fois par le parent, avant tout dispatch.
`binary = "build/{stem}"` dit où le résultat atterrit, `<dir>/<stem>` par défaut ; `build` omis si
autre chose a déjà construit. `cargo` n'a besoin de rien de tout ça : `cargo test` construit ce
qu'il lance, et `cargo metadata` liste les cibles sans rien construire.

**Un outil manquant est installé quand l'environnement est à nous.** Un provider de suite python
dont l'interprète ne l'a pas l'installe — dans un venv, un micromamba, un conteneur — et le DIT
(jamais silencieux : installer quelque chose dans l'environnement de quelqu'un est un acte). Dans
l'interprète **système** il refuse et explique quoi faire : celui-là est partagé avec tout le reste
de la machine, et ce n'est pas à errand de le changer. La détection est `sys.prefix !=
sys.base_prefix`, plus `CONDA_PREFIX`/`VIRTUAL_ENV`.

L'exemple 03 déclarait `build = "make -C cpp"` sans Makefile (remarque de l'utilisateur, juste) : il
en a un, plus le crate rust qui manquait, plus un README qui explique le modèle. Ses environnements
micromamba sont retirés — l'exemple parle d'adopter des suites, et en déclarer un faisait construire
un environnement sur la machine de qui l'essaie (constaté en le lançant).

**Et le défaut que l'exemple a révélé : mentionner errand n'est pas déclarer du travail.**
`tests/test_api.py` disait en COMMENTAIRE qu'il était collecté par errand, et le marqueur textuel
suffisait à le faire importer et exécuter. Il faut désormais un vrai import (regex sur
`from errand … import` / `import errand`), et un fichier qu'un provider possède est à ce provider
quoi qu'il importe.

134 entrées, plus rien qui saute : les trois providers sont tous exercés pour de vrai, pytest inclus
(le test fabrique un venv sans pytest et laisse le provider l'y installer).

## Dix-huitième passage — l'écran (`errand --tui`)

Demande : suivre et lancer depuis un écran ; stdout/stderr **en face** des cas ; des listes à cocher
pour garder l'esprit des matrices ; relancer une ligne d'historique.

**Trois règles, et tout le reste en découle.**

1. **L'écran ne lance rien lui-même.** Il ÉCRIT une ligne de commande errand — celle qui est
   affichée en bas — et la lance comme un enfant ordinaire. Rien que l'écran sache que la ligne de
   commande ignore, rien qu'il fasse qu'un shell ne puisse faire. `r` lance, `b` lance détaché, `!`
   édite la ligne à la main avant. Conséquence : l'historique est une liste de COMMANDES
   (`.errand/history`, une par ligne, texte nu), écrite par `main()` lui-même — donc une commande
   tapée dans un shell y apparaît, et entrée la relance. Écrite seulement du côté qui a été
   *demandé* : l'enfant d'un dispatch exécute une commande que personne n'a tapée, là-bas.

2. **L'écran lit l'arborescence de sortie, pas le tuyau.** Les chemins sont calculés AVANT que ça
   tourne (`plan_of`, la fonction même dont le registre `--batch` est fait) : le panneau en face
   d'un cas est le fichier `output.txt` de ce cas. D'où le même affichage sous `-j 8`, pour une
   machine distante, et pour un job soumis hier — trois situations où un seul flux de lignes
   entrelacées ne dit rien d'aucun cas en particulier. **Cinquième dividende de la prédiction des
   chemins.**

   Ça a demandé un changement réel : `output.txt` est désormais écrit **au fil de l'eau** (le `Tee`
   de `capture()` ouvre le fichier), plus seulement à la fin. `tail -f` marche dessus. Sous `-j`,
   avant, on ne voyait rien avant la fin de chaque enfant.

3. **Une case à cocher est une matrice.** Deux entrées, deux envs, deux valeurs d'un tag et deux
   d'un paramètre = huit runs, pour la raison exacte qui fait qu'une virgule en fait huit — et ça
   PRODUIT cette virgule. Les `choices` sont des cases ; le reste se tape, virgules comprises. Un
   filtre (`/`) cache des lignes, il n'en décoche jamais.

Détails tranchés en écrivant : les coches vivent sur l'écran et non sur les lignes (les listes sont
reconstruites deux fois par seconde) ; un titre de fichier ou de paramètre est survolé, jamais
sélectionné ; `q` refuse de partir pendant un run lancé d'ici (le tuyau se casserait sous lui) —
`--batch` est la façon prévue de survivre à la fenêtre, et `Q` arrête et sort.

**Le défaut que l'écran a révélé — et il est sérieux.** En lançant `--env plain,other`, l'écran a
montré `lost` sur les runs de `plain` : **l'environnement n'était pas dans le chemin.**
`runs/{entrée}/[params]/{place}/{date}/` avec `place = host` (préfixé du conteneur) — donc deux
environnements sur la même machine écrivaient dans la MÊME feuille, et `R.clear( leaf )` effaçait le
premier. Silencieusement, depuis le premier jour. Corrigé : `place = {env}@{host}`, l'environnement
tenant lieu de conteneur (une image est une des choses qu'un environnement EST, et le nom est celui
que le projet a choisi). Une conséquence heureuse : le lieu d'un run détaché *localement* devient
prédictible, et le registre `--batch` le dit au lieu de mettre `?`.

Tests : le pty. Un programme curses ne se teste pas en capturant sa sortie — on lui donne un vrai
terminal (`pty.openpty`, une vraie taille), on tape dedans, et on lit ce qu'il a peint. Avec
`ERRAND_TUI_REPAINT=1` il repeint chaque image en entier, sinon ncurses n'envoie que les cellules
qui CHANGENT et une phrase affichée depuis deux images n'est nulle part dans le flux. Tentative
abandonnée : reconstruire la grille (positions) — c'était écrire un émulateur de terminal, et les
tests auraient porté sur lui. On vérifie donc CE QUI a été écrit, pas où : chaque phrase est peinte
d'un seul `addnstr`.

141 entrées, tout passe.

## Dix-neuvième passage — l'écran repris sur retours d'usage, et textual

Premier essai de l'écran par l'utilisateur. Six retours, et le premier est un vrai défaut.

**« No module named 'primes' », et plus aucune entrée.** Lancé à la racine du dépôt errand, la
découverte importait `examples/01-minimal/test_primes.py`, dont le voisin `primes.py` n'est pas sur
le chemin depuis là-haut — et **un fichier qui ne s'importe pas coûtait TOUTES les autres entrées**,
parce que l'exception remontait jusqu'en haut de `select`. Corrigé en trois temps :

1. `discovery.collect` attrape par fichier et remplit `discovery.broken`
   ( chemin, la ligne courte, la trace entière ). Tolérant, pas silencieux : le runner les liste à
   la fin et **emporte le code de retour avec lui** ; l'écran leur donne une ligne chacun, avec la
   trace dans le panneau en face. Un demi-projet installé est un état de fait ordinaire ; un écran
   vide est une mauvaise façon de le dire.
2. **Un répertoire qui a son propre fichier de config est UN AUTRE PROJET**, et on n'y descend pas :
   ses entrées tourneraient avec notre `src`, nos providers et nos environnements — c'est-à-dire
   mal. ( Règle générale, pas un correctif d'exemple : ça vaut pour tout dépôt qui en contient un
   autre. )
3. **Un fichier qui déclare du travail peut importer ses voisins** : son répertoire est sur le
   chemin d'import PENDANT sa lecture, puis retiré. C'était la vraie cause de `primes`, et l'écran
   l'a rendue impossible à ignorer — sans ça, errand ne savait pas lire sa PROPRE suite depuis sa
   propre racine ( onze fichiers illisibles, tous des `from _infra import …` ). Le travail se
   déclare À CÔTÉ du code qu'il exerce ; le répertoire d'où on a lancé la commande n'a pas à changer
   ce qu'un fichier peut importer. Emprunté et rendu : un chemin laissé là déciderait de l'import de
   quelqu'un d'autre plus tard.

Et un piège trouvé en écrivant les tests : **un fichier qui déclare du travail n'est pas un module
dont on importe**. `test_tui.py` faisait `from test_session import …` — les entrées de `test_session`
se retrouvaient enregistrées DEUX fois, la seconde sous un nom de module qu'errand ne peut pas
recharger ( `KeyError` en plein `run_entries` ). Désormais c'est un échec qui s'explique, et ce qui
est partagé est dans `_demo.py`, qui ne déclare rien.

**textual.** Question posée : rester en curses stdlib et soigner le dessin, ou prendre textual.
Réponse de l'utilisateur : *textual, mais la TUI seule en a besoin — on peut proposer un pip
optionnel*. D'où `errand-run[tui]`, et `errand --tui` qui dit quoi installer quand il n'est pas là.
La propriété « zéro dépendance » du cœur est intacte, et elle reste énoncée pour ce qu'elle est :
errand CONSTRUIT les environnements, donc il doit tourner avant qu'aucun n'existe — un écran n'est
le bootstrap de personne.

Découpage qui en découle et qui vaut par lui-même : **`session.py` ( le modèle ) n'a pas une ligne
de textual**, et c'est lui qui est testé le plus. `tui.py` n'est plus que la vue. Si textual devait
sauter un jour, c'est la vue qui change, pas le reste. Le harnais pty est parti avec curses : le
pilote de textual ( `App.run_test()` ) fait le même travail sans terminal et sans émulateur.

**Les quatre autres retours, et ce qu'ils ont changé :**

- *« envs, tags et params, je pensais que ça n'apparaîtrait qu'au lancement »* — juste. Ils étaient
  des onglets permanents alors que ce sont des **questions posées une fois, au moment de lancer**.
  Il reste trois listes ( cas, runs, historique ) et **une fenêtre** : entrée sur un cas l'ouvre,
  tout y est coché à la flèche et à l'espace, entrée lance.
- *« je n'aime pas la ligne de commande en bas »* — elle est partie de l'écran. Elle survit **dans
  la fenêtre**, petite et grise : ce n'est pas une invite, c'est ce qui va se passer, dit une fois,
  pour que le jour où on en veut dans un script on sache déjà quoi écrire. Le principe ( l'écran
  n'exécute que des commandes errand ) est inchangé — il n'est simplement plus affiché comme une
  leçon.
- *« l'historique : afficher les sorties texte et les fichiers, entrée pour un `open` »* — le
  panneau en face d'une ligne montre ce qu'elle a produit **la dernière fois qu'elle a tourné** ( lu
  dans l'arborescence, pas mémorisé : cette session-là ne l'a pas lancée ), et `o` ouvre un des
  fichiers avec `xdg-open`/`open`. Un `.svg` d'expérience est à deux touches du cas qui l'a produit.
  Pas d'ouverture quand il n'y a pas d'affichage : sur une machine distante, prétendre le contraire
  bloquerait ou mentirait.
- *« comment on enlève le filtre ? »* — échap, et c'est écrit dans le pied de page ( que textual
  tient à jour tout seul, ce qui est une des raisons de le prendre ).

Un état de plus au passage : un run sans fichier résultat n'est **perdu** que si c'est NOUS qui
l'avons lancé. Une ligne d'historique jamais relancée affiche « pas encore lancé », pas « perdu » —
d'où `states_of( plan, missing )`, où l'appelant dit ce que veut dire l'absence.

## Vingtième passage — retour à curses, avec la souris

Deuxième essai par l'utilisateur, et le verdict sur textual : *« bulky »*. Question posée en
retour : *« est-ce que tu penses pouvoir faire avec curses un peu d'interaction souris (wheel,
click) ? »* Oui — `mousemask` + `getmouse`, la molette étant les boutons 4 et 5. Donc retour à
curses, et **l'extra `[tui]` disparaît** : zéro dépendance de nouveau, partout.

Ce qui rend le va-et-vient bon marché : `session.py` n'a jamais eu une ligne de textual. La vue a
été jetée deux fois, le modèle zéro.

**La gestion du focus était le vrai reproche**, et en curses le problème n'existe pas : un panneau
est ACTIF, les flèches le pilotent, tab passe au suivant, et **cliquer dans un panneau le rend
actif**. La molette fait défiler ce qui est sous le pointeur **sans déplacer le curseur** — regarder
n'est pas choisir, et une liste qui déplacerait sa sélection sous le pointeur choisirait à votre
place.

**Quatre panneaux, et la colonne de droite est « ce dont la ligne de gauche parle » :**

- `cases` — **un arbre par fichier** ( demandé ) : le fichier est l'endroit où on va chercher.
- `runs` — **runs et historique fusionnés** ( demandé ), parce que c'est une seule chose : une
  commande, et ce qu'elle a produit. Celle d'aujourd'hui est en haut et bouge encore, celle d'hier
  est trois lignes plus bas, et les deux se lisent pareil puisque les deux sont lues dans
  l'arborescence. `r` relance celle sous le curseur.
- `files` — ce que le run a écrit.
- `preview` — le fichier sous le curseur s'il est du texte ( test : décoder le début en utf-8 et
  refuser un NUL — les extensions mentent ), sinon ce qu'il est et sa taille. `output.txt` suit la
  fin tant que personne n'a fait défiler. Et quand le curseur de `cases` est sur un fichier
  illisible, c'est la TRACE qui s'affiche là : la colonne de droite parle toujours de la ligne de
  gauche.

**La fenêtre de lancement ne redemande plus quel cas** ( demandé, et c'était juste ) : entrée dans
la liste des cas EST le choix du cas. Elle demande le reste — environnements, valeurs de tags,
paramètres, `-j`, et une case `detach` qui remplace un raccourci de plus.

Deux choses apprises en testant au pty :

- **Le protocole souris se lit, il ne se suppose pas.** Le terminfo d'ici dit `kmous=\E[<` : c'est
  du SGR ( 1006 ), et ncurses n'accepte que celui-là. La séquence d'activation est
  `\E[?1006;1000h` — cherchée comme `?1000h` elle ne se trouve jamais. Le harnais lit donc dans ce
  que l'application a ÉMIS le protocole qu'elle attend.
- **« est-ce que c'est apparu » et « est-ce que ça a disparu » ne se testent pas pareil.** Accumuler
  une seconde de peinture répond à la première question et ment sur la seconde : la frame d'avant la
  touche est encore dans le tampon. D'où `frame()`, qui ne garde que ce qui suit le dernier
  effacement d'écran.

Et deux défauts que seuls les tests souris pouvaient trouver :

- **Un relâchement n'est pas un clic.** En traitant les deux, chaque clic agissait deux fois — et
  surtout le relâchement d'un cran de molette atterrissait comme un clic là où se trouvait le
  pointeur, donc la molette SÉLECTIONNAIT. Seuls les bits « pressé / cliqué » comptent maintenant.
  ( Côté harnais : un cran de molette n'a pas de relâchement, et un vrai terminal n'en envoie pas. )
- **La reconstruction des listes ramenait la vue sur le curseur.** Les listes sont refaites deux
  fois par seconde, et `reveal()` y était appelé : une demi-seconde après chaque coup de molette, la
  vue revenait d'elle-même. Le défilement et la sélection sont maintenant découplés pour de bon — le
  curseur n'est ramené à l'écran que lorsqu'il BOUGE.

Un crochet de mise au point est resté : `ERRAND_TUI_TRACE=<fichier>` note chaque touche et chaque
rapport souris. Ce n'est pas une fonctionnalité, c'est la façon de répondre en dix secondes à « est-
ce que cette touche est seulement arrivée ? » — la seule question qui vaille quand un écran ne réagit
pas. Elle a servi deux fois en une heure : la première a montré que le clic ARRIVAIT ( donc le défaut
était dans mon traitement ), la seconde que la molette arrivait bien en `0x200000`.

## Vingt-et-unième passage — deux écrans, et la recherche floue

Trois retours, tous justes.

**Un écran pour lancer, un écran pour les runs.** Les quatre panneaux sur un seul écran donnaient à
chacun la moitié d'un écran de large, et il y a plus de cas que ça. Deux pages, parce qu'il y a deux
questions : QUE LANCER, et QU'EST-CE QUE ÇA A DONNÉ. `tab` passe de l'une à l'autre. La page `cases`
a la liste à gauche et, en face, tout sur le cas sous le curseur — jusqu'à **comment il s'est passé
la dernière fois**, lu dans l'arborescence ( donc vrai après un redémarrage, et si c'est quelqu'un
d'autre qui l'a lancé ).

**La recherche floue** ( demandée : « les distances textuelles utilisées dans les IDE » ). Le nom
qui manquait : ce n'est PAS une distance d'édition. Levenshtein répond à « à quel point ces deux
chaînes diffèrent », question que personne ne pose ici : `tsq` doit trouver
`tests/test_shapes.py::quick`, dont la distance d'édition est énorme. Ce que fait un
« go to file » d'IDE, et ce que fait `errand/fuzzy.py`, c'est **une sous-séquence** — les lettres
dans l'ordre mais pas forcément ensemble — **puis un SCORE** : ensemble bat dispersé, début de mot
bat milieu de mot, tôt bat tard, court bat long. Programmation dynamique mémoïsée sur
( où dans l'aiguille, où dans la botte, la lettre précédente est-elle juste avant ) — sans quoi
essayer tous les placements coûterait exponentiel, et il FAUT les essayer tous : le premier
placement d'une lettre n'est pas le meilleur ( le `s` de `tests/shapes` doit pouvoir atteindre
`shapes` ).

Trois décisions qui comptent autant que l'algorithme :

- **Plusieurs mots = plusieurs recherches, toutes obligatoires**, chacune pouvant être trouvée dans
  un champ différent : `shp gpu` = « un cas dont le nom ressemble à shp ET dont les tags ou le
  fichier disent gpu ». Ajouter un mot resserre ; on ne réécrit jamais ce qu'on a tapé.
- **Les positions qui ont matché reviennent avec le score**, et sont affichées en gras : une liste
  qui dit POURQUOI une ligne y est est une liste qu'on croit d'un coup d'œil.
- **Taper EST la recherche** — pas de touche à presser d'abord. D'où une petite machine à états :
  `esc` lâche la recherche **sans la jeter** ( la liste reste resserrée pendant qu'on la parcourt et
  qu'on coche à l'espace ), un deuxième `esc` l'efface, un troisième quitte. Et l'espace n'est un
  séparateur de mots que tant qu'on tape ; une fois lâché, il coche.

**La fenêtre ne redemande plus quel cas** : entrer dans la liste EST le choix du cas ( déjà fait au
passage précédent, confirmé ici ).

Le module `fuzzy.py` ne connaît ni écran ni session : sept entrées le testent seul, en quelques
millisecondes. C'est la troisième fois que le découpage paie — la vue a été jetée deux fois et
remaniée une troisième, le modèle jamais.

## Les tags — première version, dépassée par le point 3 ci-dessus

`Driver("jax", pip=…)` faisait quatre choses à la fois. Elles se séparent en deux :

- **`Tag( name, value = None )`**, pure métadonnée : `Tag("jax")`, `Tag("fp","64")`. Un tag DIT ce
  qu'est un env.
- **`Pip( spec )`**, un layer à part : ce que `install` pose dans l'env avant tout le reste. Ça
  n'avait rien à faire sur une étiquette, et ça se généralise (un env peut en vouloir deux).

Un seul langage d'expression, lu à **trois endroits** :

```bash
./run bench cost --tag 'jax & fp=64'      # 1. choisir l'env
./run test --only 'slow & !gpu'           # 3. filtrer les entrées, par leurs tags à elles
```
```python
if not has_tag( "torch" ): sys.exit( 0 )  # 2. se retirer avant l'import, à la place de driver_is
tag( "fp" )                               #    -> "64" | None
```

Grammaire : conjonction de littéraux, chacun éventuellement nié — `&` et `!`, pas de `|`, pas de
parenthèses. Justification à garder : **choisir où tourner est un acte de RESSERREMENT, et une
disjonction ne resserre pas.** L'expression doit désigner UN env ; si plusieurs qualifient, erreur
qui les liste. `--tag a --tag b` répété = la même conjonction, pour échapper au quoting du shell.

Hors du runner, `has_tag` répond oui à tout (même règle qu'aujourd'hui : faire disparaître des tests
en silence est pire qu'un import qui tombe bruyamment).

**Tag contre option**, la phrase à retenir : *un tag CHOISIT l'environnement, une option change ce
qui se passe DEDANS*. Une option ne participe jamais à la sélection. Si on veut que `--fp` choisisse
entre deux envs, alors ce n'est pas une option, c'est `Tag("fp","64")` sur les deux.

## À corriger au passage

`cmd_test`/`cmd_bench`/`cmd_experiment` sont 90 % du même copier-coller, et ça a déjà coûté un bug :
dans `cmd_experiment` (`loom/src/loom/cli/main.py:775-783`), la branche distante a l'appel sorti de
la boucle de balayage — `rc = run_in_env(...)` est sous le `if env_cfg and env_cfg.driver:` du
niveau au-dessus. Un balayage distant ne lance donc qu'UNE combinaison, et rien du tout si l'env n'a
pas de `Driver`. Le chemin `bench` équivalent est correct. Les trois commandes deviennent un seul

Autres reprises dues au passage : la racine du dépôt par marqueur remonté depuis `cwd` (et `--root`)

au lieu de `SDOT_` en dur ; les variables d'environnement redevenant le TRANSPORT à travers ssh et
non l'API locale ; le marqueur de découverte textuel (`"loom.testing"` grepé dans les fichiers)
devenant le nom du paquet, plus ce que le shim de compat impose de reconnaître en plus.

## Vingt-deuxième passage — tab est un rectangle, et l'arborescence est celle du disque

Deux retours d'usage, deux corrections de même nature : l'écran cessait de décrire ce qu'il montre.

`tab` changeait de page. On attend de `tab` qu'il passe au rectangle suivant — c'est ce qu'il fait
partout ailleurs — et il fallait donc tenir deux idées à la fois pour se déplacer d'un cran : quel
panneau, et quelle page. La sortie n'est pas de trouver une autre touche pour les pages : **une page
n'est pas un mode, c'est l'endroit où habite le rectangle où l'on est**. Les deux rectangles de
`cases` et les trois de `runs` forment un seul anneau ; sortir du dernier de `cases` tombe sur
`runs`, et l'écran suit. Le concept de page disparaît de ce que l'usager a à savoir, sans disparaître
de l'écran : les deux noms en haut restent, et cliquer l'un d'eux y va directement.

Les cas étaient un arbre par fichier, à plat : trois cents cas devenaient quatre-vingts lignes de
`bench/gpu/heavy.py` complets, et le chemin le plus long noyait le reste. Ils sont maintenant
l'arborescence du disque, répertoire par répertoire — **un projet est une disposition avant d'être
une liste**, et le répertoire est la façon dont on se souvient d'où vit un cas. Avec une règle :
*un répertoire qui ne contient qu'une seule chose ne coûte pas sa ligne*, son nom rejoint celui de
son enfant (`bench/gpu/heavy.py` sur une ligne). Une ligne qu'on ne peut que traverser ne dit rien.
La compression se fait à la descente (`_branch`), pas sur l'arbre : c'est trois lignes au lieu d'une
passe de réécriture, et le pli (`folded`) reste posé sur un chemin réel, donc survit au rebâtissage
deux fois par seconde.

## Vingt-troisième passage — une touche de fonction par rectangle, et une ligne par option

`tab` qui parcourt l'anneau des rectangles ne valait pas mieux que `tab` qui changeait de page : on
arrive quelque part en appuyant sur la même touche jusqu'à y être, ce qui n'est pas y aller. Il y a
douze touches de fonction et cinq rectangles. **Une touche par rectangle, écrite dans le titre du
rectangle qu'elle ouvre** (`F1 cases`, `F2 about`, `F3 runs`, `F4 files`, `F5 preview`) : rien à
retenir, puisque la touche est écrite là où elle mène, et rien à parcourir. La page suit le
rectangle. `tab` reste le rectangle voisin *de la page où l'on est*. Le reste des verbes prend les
touches suivantes — F6 relire, F7 relancer, F8 interrompre, F9 ouvrir, F10 les touches, F12 partir —
et les lettres `r o x q` restent des alias sur la page des runs.

La fenêtre de lancement était illisible parce qu'une option y coûtait deux lignes : le nom sur
l'une, la valeur sur l'autre. **Une option est une ligne, toujours les trois mêmes colonnes** : le
drapeau à gauche, le champ au milieu, ce que ça veut dire à droite, en grisé. Un œil qui a lu une
ligne les a toutes lues, et il y a de la largeur à revendre. Trois choses qui se ressemblaient sont
maintenant distinctes à l'œil : ce qu'on a **tapé** est en gras, ce qui se passera **de toute façon**
est le défaut en gris à la même place, et **la commande finale** est sous un filet, dans sa propre
couleur, hors du flux des options. Les raccourcis, eux, restent sur la ligne du bas de l'écran, là
où ils sont toujours. Un curseur clignote dans le champ courant : c'est la seule façon de dire
« tapez ici » que personne n'a besoin d'apprendre.

Au passage, un défaut que le test a révélé et pas l'œil : les listes n'étaient rebâties que deux fois
par seconde, donc un pli ou une coche pouvait mettre une demi-seconde à s'afficher — ce qui se
ressent comme une touche perdue. Une touche marque maintenant l'écran `dirty` et la reconstruction
a lieu tout de suite. Côté banc d'essai, `frame()` rendait *ce qui a été peint jusqu'ici*, parfois
un demi-écran ; il rend maintenant la dernière image **complète**, celle qui est entre deux effacements.

## Vingt-quatrième passage — les lettres sont la recherche, donc les verbes sont les touches de fonction

Une touche par rectangle était encore une touche de trop à retenir : `tab` suffit pour aller à côté.
Les douze touches de fonction servent maintenant aux **verbes**, ce qui tombe bien puisque les
lettres sont prises : sur les deux pages, **taper est la recherche**. F1 les touches, F2/F3 la page
d'avant et la page d'après (deux pages, deux touches voisines : rien à viser, seulement une
direction), F5 relancer la dernière commande, F6 celle sous le curseur, F7 interrompre, F8 ouvrir le
fichier, F9 relire le projet, F12 partir.

`esc` commence par effacer ce qui a été tapé, et seulement ensuite quitte : **un filtre est ce dont
on veut le plus se débarrasser**, ça ne peut pas être la chose la plus difficile à enlever. L'état
« lâcher la recherche en la gardant » que j'avais inventé disparaît ; tant qu'une recherche est en
cours, l'espace est un séparateur de mots et la coche devient `ctrl-espace` (ou un clic sur la case).

La page des runs a sa recherche elle aussi, sur les commandes — *un historique ne sert qu'à partir du
moment où on peut y retrouver une ligne*. Les deux recherches sont séparées : celle qu'on garde sur
`cases` est encore là au retour de `runs`.

Deux petites choses vues du même coup. `C_DIM` était initialisée à la couleur par défaut, c'est-à-dire
à *rien* : tout ce qui devait être « en gris » (les aides des paramètres dans la fenêtre de
lancement, les tailles, les détails) s'affichait comme du texte ordinaire. Une fonction `dim()` porte
maintenant `A_DIM` avec la paire, et il n'y a plus qu'un endroit où le dire. Et `result.yaml` gagne
`date` : le répertoire porte le JOUR, ce qu'un chemin peut porter en restant lisible, donc le
registre doit porter l'heure, avec son décalage — deux runs du même cas le même jour tombent dans le
même répertoire, et c'est le seul champ qui les distingue.

## Vingt-cinquième passage — deux répertoires pour trouver un cas, une liste plate pour ses runs

L'arborescence était `runs/{fichier}__{nom}/{hash des paramètres}/{place}/{jour}/`. Un niveau par
dimension : ça se dessine très bien dans un README et ça se parcourt très mal au `cd`, et le niveau
dont le nom était un hash ne se lisait pas du tout — il fallait le fichier de résultat pour savoir
ce qu'il désignait.

Elle est maintenant :

    runs/{fichier}/{nom}/{quand}-{place}[-{paramètres}]/
    runs/solvers/cost/2026-09-25_18h04m11-gpu@gpu-box-method=newton,n=5000/

**Le fichier et le nom sont la façon dont on CHERCHE un cas** — c'est ce qu'on tape pour le lancer —
donc ce sont des répertoires. Tout ce qui distingue deux *runs* du même cas tient dans un seul nom,
dans l'ordre où on le dirait : quand, où, avec quoi. Une matrice donne plus de *noms*, jamais plus de
niveaux. Les paramètres sont en clair (`method=newton,n=5000`), coupés à une largeur lisible avec un
hash court au bout quand il y en a plus que personne n'en lit — l'illisible devient le dernier
recours d'un nom qui a déjà dit l'essentiel, au lieu d'être tout le nom.

La difficulté était ailleurs : **le chemin doit être prévisible avant que le run existe** (c'est ce
qui fait marcher le rsync ciblé, le registre du `--batch`, et l'écran qui suit la sortie). Mettre
l'heure dans le nom, c'est deux processus qui calculent deux noms différents. D'où `stamp()` : **un
horodatage pour toute l'invocation**, calculé une fois et posé dans l'environnement, donc hérité par
les enfants de `-j 8`, par le job que l'ordonnanceur démarrera demain et par le run distant. Le nom
prédit est le nom écrit.

Conséquence assumée : `latest` désigne désormais le dernier run du cas, quelle que soit sa place et
ses paramètres, au lieu d'un `latest` par (place, paramètres). Pour une expérience qu'on relance dans
une seule configuration à la fois — ce que `stable_path` vise — c'est exactement ce qu'on veut ; pour
une matrice, `latest` bascule. À revoir si ça gêne.

## Vingt-sixième passage — loom, sdot et otrec branchés dessus

296 entrées Python et 5 fichiers de tests C++ sont passés de `loom.testing` + `loom.cli.main` à
`errand`. Ce que ça a coûté, fichier par fichier, est une ligne d'import : `from loom.testing
import test, bench, Param` devient `from errand import ...`, et `check_grad` reste chez loom,
qui est le seul à qui il appartient. Le reste de `loom/src/loom/testing/__init__.py` — 239 lignes
d'enregistrement en deux phases, de résolution de paramètres par variables d'environnement, de
`driver_is` — a disparu : c'est errand, et errand ne sait rien de loom.

Trois traductions de vocabulaire, qui sont trois décisions :

* **Le driver n'est plus une couche, c'est un tag.** `Driver("jax")` ne changeait pas la façon
  d'atteindre la machine, il disait ce qu'on y trouve. Donc `env( "nsdot", [ ... ], driver =
  "jax" )` : ça sélectionne (`--driver torch`), ça apparaît dans `result.yaml` et dans le nom du
  répertoire, et le fichier qui a besoin de savoir demande `has_tag( "driver=torch" )` au lieu de
  lire `SDOT_DRIVER`.
* **`info`/`infox`/`new_batch_axis` ne sont plus posés dans `builtins`.** Un nom qui apparaît sans
  avoir été importé est une dette qu'on paie en cherchant d'où il vient ; deux fichiers les
  importent maintenant comme tout le monde.
* **Les tests C++ sont un provider**, pas un cas particulier du runner. Une entrée par fichier —
  les entrées doivent être connues de ce côté-ci d'un saut ssh, avant toute compilation, pour que
  les chemins à rapatrier soient calculables d'avance — et le device est un *paramètre*
  (`--device cpu,cuda`), donc une matrice comme une autre, avec un répertoire par device. Un
  device absent donne un SKIP. `provider()` prend 60 lignes dans `errandfile.py`, et tout ce qui
  entoure le run est celui de tout le monde.

`./run` ne garde que ce qui FABRIQUE la machine (install, toolchain, build-sif, env create) :
1178 lignes tombent à 322. Reste une duplication à résoudre : les environnements sont déclarés
deux fois, dans `.envs.py` pour `./run` et dans `errandfile.py` pour errand. `errand --setup`
sait créer un env micromamba et bâtir une image ; ce qui manque pour supprimer `.envs.py` est le
`--fakeroot` et le scratch dir des builds d'images distantes.

## Deux défauts d'errand trouvés en s'en servant pour de vrai — dont un qui coûte cher

**Un environnement qui existe ne se reconstruit pas dans le dos de celui qui l'a fait.** Première
commande `errand` dans ce dépôt : `setup.ensure` a vu un env `nsdot` dont il n'avait aucune trace,
en a conclu « périmé » et a lancé `micromamba create -y -n nsdot python=3.13 …` sur un
environnement qui existait et marchait. `create` sur un env existant n'est ni un no-op ni une
mise à jour : il y résout les specs nommées, et `python=3.13` posé sur un env en 3.14 emporte avec
lui numpy, jax et tous les editables. J'ai détruit deux environnements de la machine comme ça.

Le défaut n'est pas dans la déclaration, il est dans la lecture : **« périmé parce que rien n'a
jamais été enregistré » n'est pas « périmé parce que la déclaration a changé »**. Présent et jamais
vu se lit maintenant comme *adopté* — on enregistre l'empreinte et on ne touche à rien ; seule une
déclaration qui a changé depuis un enregistrement qu'errand a écrit LUI-MÊME est une raison d'agir,
et `--setup force` est la façon de dire l'autre chose. En prime, `Micromamba.build` fait `install`
quand l'env est là et `create` seulement quand il n'y est pas : même sous `force`, on n'efface plus.
Et `--envs` ne dit plus « stale » de ce qu'il va adopter — annoncer un travail qui n'aura pas lieu
est une autre façon de mentir.

**Un dépôt à l'intérieur d'un autre a besoin de dire où il commence.** errand n'a besoin d'aucune
configuration, donc son propre dépôt n'avait pas de fichier de projet — et posé dans ce monorepo,
il se faisait lire comme un répertoire de celui-ci (ses 167 entrées sortaient dans `errand`
lancé d'en haut, et `errand` lancé de dedans remontait chercher la racine au-dessus). Un
`errandfile.py` de trois lignes chez lui tranche les deux sens à la fois : c'est la même règle
— « la racine est le premier répertoire au-dessus qui en a un » — qui donne la bonne réponse des
deux côtés.

## Vingt-septième passage — le vieux lanceur supprimé, et ce qu'il a fallu pour ça

Objectif : plus de script `run` du tout. Il lui restait quatre choses, et chacune a trouvé sa place.

**Bâtir une image.** L'ancien `build-sif` avait `--fakeroot`, `--scratch-dir`, et le build distant.
Ces trois-là ne sont pas des options de ligne de commande, ce sont des **propriétés de l'image** :
elles ne changent pas d'une invocation à l'autre, elles disent comment CETTE image se fabrique.
Donc `Apptainer( fakeroot = True, scratch = "/data/…", build_flags = [ … ] )`, à côté de `flags`
et `mounts` qui disent, eux, comment on y ENTRE. Le scratch part dans `APPTAINER_TMPDIR` *et*
`APPTAINER_CACHEDIR` — apptainer déballe ses couches dans l'un, télécharge dans l'autre, et un
build qui manque de place dans l'un ou l'autre meurt pareil. Le build distant : `setup.ensure`
pousse les sources en rsync avant de lancer les étapes par-dessus ssh, parce que la recette est un
fichier ICI et que le build a lieu LÀ-BAS. Et `ssh -t`, parce qu'un build demande un mot de passe
et affiche une barre de progression que personne ne voit sans terminal.

**Installer.** C'était `pip install -e` des projets dans l'ordre : c'est la liste `pip` de la
couche, et `errand --setup` s'en charge. Rien à écrire de plus.

**Entrer dans un environnement pour autre chose.** La sous-commande `toolchain` n'était que
« lance CETTE commande dans CET environnement ». D'où `errand --env X -- <commande>` : tout ce qui
suit un `--` nu est une commande à lancer là-bas. Ce n'est pas vraiment une fonction du runner,
c'est une fonction des environnements — ils sont déjà décrits ici, une fois, avec les couches qui y
mènent ; se faire ouvrir la porte est une plus petite chose qu'un second outil qui les redécrirait
tous.

Ça a demandé une correction qui traînait : chaque couche remplaçait `argv[0]` par son interpréteur,
en dur. Juste pour un appel d'interpréteur, faux pour `nvidia-smi`, qui devenait `python
nvidia-smi`. `layers.under( argv, python )` ne remplace le premier mot que **s'il nomme un
interpréteur**, et le garde sinon. Et la commande reçoit le `PYTHONPATH` du projet : se faire
ouvrir la porte pour regarder le checkout de quelqu'un d'autre n'aurait servi à rien.

**Lister / créer les environnements.** `errand --envs` et `errand --setup`, qui existaient déjà.

Reste la question que `.envs.py` réglait en étant hors de git : ce qui diffère d'une machine à
l'autre. La réponse est `errand.local.py`, qui servait déjà aux entrées (`need`), et qui sert
maintenant aussi au fichier de projet — avec `value( clé, défaut )` et non `need` : **une entrée a
le droit de ne pas tourner, un fichier de projet n'a pas ce droit**, il est lu une fois, avant
tout, et ce qu'il ne trouve pas il doit s'en passer. D'où le nom d'hôte et le scratch en clair dans
`errandfile.py` comme défauts, surchargeables sans toucher à git. Le fichier local est désormais lu
AVANT la configuration, ce qui est le seul ordre qui rende ça possible.

Bilan : le script `run`, `loom/src/loom/cli/` (main, envs, layers : 1676 lignes) et `.envs.py`
supprimés.
